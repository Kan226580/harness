## 写在前面：这份手册为什么这么长

这份手册的第一版写得像一份提纲：句子短、术语多、默认你已经知道很多东西，结果读起来像一串密码。这一版把那些"默认你懂"的内容全部补出来了。

在接下来的每一个步骤里，你都会看到六个部分，它们各自回答一个问题：

1. **这一步要解决什么问题**：用完整的话说明为什么现在要做这件事，它和前后步骤是什么关系。
2. **动手之前先弄懂几个词**：把这一步新出现的术语解释清楚，并给出在这个项目里的具体含义。
3. **具体怎么做**：一步一步列出操作，包括要执行的命令、要创建的文件，以及运行之后你应该看到什么结果。
4. **怎么算做完了**：一份检查清单，每一项都能当场验证，全部通过才能进入下一步。
5. **常见问题和提醒**：新手在这一步最容易犯的错误，以及出错后先检查什么。
6. **这一步和企业开发的关系**：在真实公司里，这件事由谁负责、叫什么名字、为什么要这么做。

**关于阅读方式的三条建议：**

第一，不要试图一口气读完这份手册。它更像一本菜谱，而不是一本小说。你应该读一章、做一章，做完当前阶段之后再回来读下一章。

第二，每个步骤通常需要一到三天完成（按每天两到四小时计算）。如果一个步骤超过三天还没有通过验收，说明它对你来说还是太大，你应该把它拆成更小的任务，而不是硬扛。

第三，遇到不懂的词，先查第 10 章的术语表；遇到报错或者卡住，先看第 9 章的自救指南；遇到设计上的疑问，回到四份设计文档里找答案。

## 第 0 章 开始之前：怎么使用这份手册

### 0.1 这份手册适合谁

如果你符合下面这些描述，这份手册就是为你写的：

- 你学过一点编程，但从来没有独立完成过一个真实项目。
- 你看到"数据库迁移""消息队列""多租户隔离"这些词会紧张，不知道它们具体是什么意思。
- 你知道大概要学 Python、前端、数据库，但不知道先学哪个、学到什么程度可以开始写。
- 你希望做完这个项目之后，不仅能演示，还能在面试里讲清楚"为什么这么设计"。

如果你已经能独立完成全栈项目，只是想了解这个项目的架构决策，那么这份手册可能对你的帮助有限，你应该直接阅读四份设计文档。

### 0.2 为什么必须一步一步来

这份手册把整个项目分成了 26 个步骤，每一步都配了一份"完成标准"。很多人会想跳过前面的基础步骤，直接去做最难的"AI 生成"部分。请不要这样做，原因有三个。

**第一个原因：后面的步骤建立在前面的步骤之上。** 比如"生成一章内容"这个功能，需要先有资料解析、要求确认、基准快照、检索、模型网关、运行记录这些东西。如果前面任何一环是假的，生成功能就只能在假数据上跑，你无法判断它到底能不能用于真实业务。

**第二个原因：错误会复利。** 假设你在第三步没有把数据库迁移管理好，而是手工用客户端改表结构。到了第十五步，你的数据库结构和代码里的定义已经对不上了，你会花好几天去排查一个原本五分钟就能解决的问题。工程上有一句话：**现在省下的时间，将来会以三倍的利息还回去。**

**第三个原因：每一步都要有一个看得见的结果。** 学习编程最怕的是"学了很久，但说不清自己会了什么"。这份手册保证你每一步结束时，都能在浏览器或命令行里演示一个真实可见的结果。这种不断的正反馈，是你能坚持几个月的关键。

### 0.3 每个步骤的固定学习流程

不管是简单的步骤还是复杂的步骤，都按照下面五段来推进。我以第三步"A3 数据库、迁移与集成测试"为例，解释每一段具体做什么。

**第一段：预习（大约占这一步总时间的 15%）。** 打开这一步指定的设计文档章节，读完它，并回答自己一个问题："这部分内容在解决什么问题？"例如 A3 指定阅读《数据库文档》第 2、5、16 节，读完之后你应该能用自己的话说出："数据库要放在容器里跑，表结构要用迁移脚本管理，不能手工改。"

**第二段：拆任务（大约占 5%）。** 把这一步拆成三到七个"半天能完成"的小任务，写进你的任务清单或者 GitHub Issue。例如 A3 可以拆成：搭好 Docker Compose、写好第一个迁移、跑通集成测试、把测试接进 CI。拆任务的意义是让你每天都有明确的终点，而不是面对一个模糊的大目标发呆。

**第三段：动手（大约占 60%）。** 按顺序完成每个小任务。每完成一个小任务就运行一次测试、提交一次代码。不要攒一大堆改动再一起测试，那样出错之后你很难定位是哪一处引起的。

**第四段：验收（大约占 15%）。** 打开这一步的"完成标准"，逐条检查。检查必须是可执行的，例如"运行 `alembic upgrade head`，输出没有报错"，而不是"感觉自己懂了"。同时，你要主动测试失败情况，例如故意输入一个错误的参数，看看系统会不会给出清楚的提示。

**第五段：复盘（大约占 5%）。** 用几句话记录：这一步我卡在哪里、怎么解决的、有什么经验值得记住、下一步要注意什么。把这些记录放在 `docs/notes/` 目录里。几个月后回头看，你会感谢现在的自己。

### 0.4 需要投入多少时间

这个项目的学习加开发总时间，对零基础的开发者来说大约是 **400 到 550 小时**。这个数字包含查资料、调试报错、写测试和写文档的时间，不只是敲代码的时间。

按照每周投入的时间不同，有三种推进方案：

| 方案 | 每周投入 | 预计总时长 | 适合什么情况 |
|---|---|---|---|
| 稳健方案（推荐） | 15 小时左右 | 6 到 8 个月 | 有工作或学业，每天能挤出两小时 |
| 加速方案 | 25 到 30 小时 | 4 到 5 个月 | 时间比较自由，能每天投入四小时以上 |
| 冲刺方案 | 40 小时以上 | 8 到 10 周 | 有导师带，或者已有一定基础，参考附录 F |

我不建议"平时不动、周末突击十二个小时"这种节奏。编程学习依赖重复和连续性：每天两小时、连续五天，效果远好于周末一次性十小时。因为遗忘曲线是真实存在的，你今天学会的东西，隔一周再看会忘掉一大半。

判断自己进度是否正常，不要看"我学了几个月"，而要看门禁：只要 G1、G2、G3、G4、G5 这五道门禁逐个通过，你就一定在正确的路上，不必和别人比较速度。

### 0.5 现在就可以开始的三件小事

如果你现在就想动手，可以先用三十分钟做下面三件事。它们都不需要写代码，但会让你对项目有一个真实的开始。

**第一件事：读三节文档。** 打开 [开发方案.md](./开发方案.md)，用十五分钟只读三节：第 2 节"产品定位"、第 4.2 节"主流程"、第 5 节"总体架构"。读的时候不需要看懂所有技术名词，只需要回答一个问题："这个产品是给谁用的，帮他们解决什么麻烦？"

**第二件事：写下第一条架构决策记录。** 在你的项目目录里新建 `docs/adr/` 文件夹，在里面创建第一个文件 `0001-模块化单体.md`，内容可以参考下面的格式：

```markdown
# ADR-0001：采用模块化单体架构

- 状态：已接受
- 日期：2026-10-08

## 背景
这个项目由一个人开发，未来需要部署在一台服务器上做演示。
如果一开始就拆成多个微服务，部署、调试和保证数据一致性的成本会非常高。

## 决策
采用"模块化单体"：所有业务模块放在同一个后端程序里，
但模块之间通过清晰的边界和接口调用，不互相直接读写内部数据。

## 后果
好处是开发、部署、调试都简单，事务也容易保证。
代价是将来如果某个模块需要独立扩容，要付出一次拆分成本。
目前项目规模很小，这个代价可以接受。
```

这个文件看起来简单，但它是企业开发中的标准做法，名字叫 **ADR（Architecture Decision Record，架构决策记录）**。它的作用是：几个月后有人问你"为什么不用微服务"，你不需要凭记忆回答，直接打开这个文件就行。

**第三件事：检查你的电脑环境。** 打开 PowerShell，逐条运行下面的命令，把结果记在 `docs/notes/environment.md` 里：

```powershell
node -v
npm -v
python --version
uv --version
git --version
docker --version
docker compose version
```

这些命令分别用来查看 Node.js、npm、Python、uv、Git、Docker 的版本。现在看不懂它们没关系，第 3 章会逐一解释每一个工具是做什么的，以及缺少哪个应该怎么安装。

### 0.6 遇到看不懂的内容怎么办

你一定会遇到看不懂的内容，这很正常。按照下面的顺序去解决，不要一上来就到处问人。

**第一步：查术语表。** 这份手册第 10 章整理了项目里会出现的术语，每个术语都有一句完整解释。很多困惑只是"这个词不认识"，查完就通了。

**第二步：查四份设计文档。** 这份手册负责"怎么学、怎么做"，四份设计文档负责"为什么这么设计"。如果某一步的说明让你疑惑，通常是因为你还没读对应的设计章节。

**第三步：查官方文档。** 技术问题优先看官方文档，而不是看博客。因为博客可能写的是三年前的旧版本，方法早就变了。每个步骤的"动手之前"部分都会给出对应的官方文档链接。

**第四步：搜索报错信息。** 把报错的最后一行复制到搜索引擎里，去掉你项目里特有的路径和编号。不要搜索整段中文描述，要搜索程序输出的英文原文。

**第五步：向 AI 提问。** 提问时务必带上五个要素：你想做什么、你运行了什么命令、完整的报错信息、你已经试过什么、你用的是哪个版本。缺少这些信息，再聪明的人也帮不了你。可以套用这个模板：

```text
我想做的事情：……
我运行的命令或代码：……
完整的报错信息：……
我已经尝试过：……
我的环境：Windows、Python 3.12、……
```

**三十分钟法则**：如果你按照上面的顺序折腾了三十分钟还没有解决，就把问题记录在 `docs/questions.md` 里，写清楚"现象、已排除的可能、下一步猜想"，然后去做别的小任务。不要为了一个问题耗掉一整个晚上，那样只会打击你的信心。很多问题睡一觉之后，或者在你做别的事情时，会突然想通。

### 0.7 要不要先把 Python 学完再开始

不要。你永远学不完，而且脱离项目学编程，学着学着就忘了。

正确的做法是"最小前置加边做边学"。在正式开始写后端之前（也就是做到 A2 步骤之前），你只需要掌握下面这些 Python 基础知识：

- 变量、字符串、数字、列表、字典这些基本类型怎么用。
- 函数怎么写、参数怎么传、返回值怎么用。
- 类是什么，怎么定义一个类，怎么创建对象。
- 模块和包是什么，`import` 语句怎么用。
- 异常是什么，`try / except` 怎么用。
- 类型注解是什么，例如 `name: str` 和 `def add(a: int, b: int) -> int`。
- 虚拟环境是什么，为什么每个项目要用独立的环境。

这些内容如果每天学两小时，大约一到两周可以掌握到"够用"的程度。其他的知识，例如异步、装饰器、元类、性能优化，全部可以在项目的具体步骤里再学。

前端也一样。你不需要先系统学完 React 再来做 A7，只需要在做到 A7 之前花几个小时了解：组件是什么、props 是什么、状态是什么、事件怎么处理。剩下的在写页面的时候自然会遇到。

## 第 1 章 先看懂项目：我们到底在做什么

### 1.1 从一个真实的工作场景说起

在动手写代码之前，你需要先理解这个产品服务的到底是什么人、解决的是什么问题。我们用一个具体的人来举例。

王工是一家施工企业的技术负责人。某天公司决定投标一个市政道路项目，招标文件发下来，一共三百多页。王工要在两周内交出一份两百页左右的技术标，内容包括施工方案、进度安排、质量保证措施、安全文明施工措施、人员设备配置等章节。

这两周里，他要反复做这些事：

第一，把招标文件从头到尾读好几遍，把"必须响应"的条款、评分项、工期和质量目标一条条摘出来。漏掉一条强制性要求，投标文件可能直接被判定为无效。

第二，从公司的资料库里翻找以往的标书、人员证书、设备清单、业绩合同，看看哪些内容可以复用。这些资料散落在不同人的电脑和网盘里，找起来非常费时间。

第三，一段一段地写正文。写的时候要小心，不能把别的项目的人员和设备写进来，也不能编造公司没有的业绩。技术标里的每一句话，评分专家都可能追问依据。

第四，写完还要自查：招标文件里的每条要求都响应了吗？评分项覆盖了吗？工期前后一致吗？引用的规范标准是现行有效的吗？

第五，排版、导出、打印、装订。

现在市面上的通用 AI 工具能帮上一部分忙，但用起来有三个明显问题。

第一个问题是**没有出处**。AI 写出来一段话，你不知道它是根据招标文件里的哪一句写的，还是它自己编的。在投标这种高风险场景里，没有出处的内容不敢用。

第二个问题是**容易编造事实**。你让 AI 写"本项目投入的主要人员"，它可能编出几个根本不存在的项目经理，或者把公司没有的业绩写进去。这类错误一旦进入投标文件，后果非常严重。

第三个问题是**没有协作和版本管理**。公司里写标书的是一个人，审核的是另一个人，AI 生成的内容改了哪一版、谁审过、审的是哪一版，全靠聊天记录和文件名区分，混乱且无法追溯。

我们要做的产品，就是针对这三个问题设计的。

### 1.2 这个产品的一句话定义

这个产品的定位是：**面向工程技术标的、具备证据追溯与人工审核能力的 AI 撰写工作台**。

这句话里有四个关键词，我们一个一个拆开解释。

**工程技术标**：指的是投标文件里的技术部分，不包含报价和商务条款。这个项目只服务技术标写作，不做报价计算、工程量清单计价、图纸理解、电子签章这些事情。把这些范围明确排除掉，是为了让第一版做得完、做得好。

**证据追溯**：系统里出现的每一条要求、每一个事实、每一段生成的文字，都要能指回它的来源。比如正文里写了"本工程总工期为 180 天"，系统要能告诉你这句话来自招标文件第 12 页的哪个段落；如果这句是人工写的而不是从资料里来的，系统也要如实标注为"人工内容"。

**人工审核**：AI 生成的内容永远是"候选草稿"，不会自动变成正式内容。系统负责发现问题和风险，人负责做最终判断。审核动作会留下记录：谁、在什么时候、基于哪份审查报告、批准了哪个版本。

**撰写工作台**：它不是聊天窗口，而是一个工作平台。你的成果不是聊天记录，而是可长期保存和追踪的资产：要求清单、项目基准、章节版本、引用证据、审查报告、审核记录、导出文件。

### 1.3 产品主流程：六个环节逐一解释

整个产品围绕一条主流程运转。下面我把这条流程拆成六步，每一步都说明"用户做什么""系统做什么""为什么需要这一步"以及"这一步会留下什么"。

**第一步：创建项目。**

用户新建一个项目，填写工程名称和工程类型（例如市政道路工程），系统自动建立项目的章节目录骨架，例如施工方案、进度安排、质量保证、安全文明施工、资源配置。

这一步看起来简单，但它是后面所有数据的容器。项目建好之后，资料、要求、基准、章节、运行记录都会挂在这个项目下面。

**第二步：上传资料。**

用户上传四种类型的文件：招标文件（tender）、企业资料（enterprise）、历史标书（historical）、参考资料（reference）。系统会检查文件大小和格式，把原件保存到私有的文件存储中，并计算文件的"指纹"（哈希值）用来防止内容被悄悄替换。

这里有一个重要的业务规则：招标文件必须绑定到具体项目，而企业资料、历史标书、参考资料可以由整个组织共享。原因是招标文件只对那一个项目有效，而企业资料是公司级别的资产。

**第三步：解析与确认。**

上传的 PDF 或 DOCX 对计算机来说只是一堆字节，系统看不懂里面的内容。所以系统要先把文件"解析"成结构化的内容块：标题、段落、表格，以及每个块在原文里的位置，例如"第 12 页的某个区域"或者"某个标题下面的第 3 段"。

解析完成后，用户要逐一确认这些资料是否可以使用、是否允许发送给云端模型处理。系统不允许在未经确认的情况下把资料内容发送出去，这是一条硬性规定。

**第四步：分析招标文件，发布项目基准。**

系统从招标文件里抽取"要求"和"事实"。要求包括强制性要求、评分项和一般要求；事实包括工期、质量目标、工程规模这类明确的信息。

抽取出来的内容一开始都是"草稿"状态，必须由人工检查、修改、确认。注意：系统只记录原文里明确写出来的信息，原文没写的一律留空，绝对不会自己猜测。企业事实只能来自企业资料，不能从历史标书里"猜"出来。

当用户确认完要求和事实之后，就可以"发布基准"。基准这个词听起来抽象，你可以把它理解成**给当前的确认结果拍一张照片并存档**。这张照片里包含当时确认的全部要求、事实、资料版本和章节映射关系，之后不可修改。

为什么需要这张照片？因为写标书是一个持续几周的过程，期间要求和资料可能会变。如果审核的时候用的是"当前最新的数据"，那么数据一变，之前的审核就失去意义了。有了基准，审查、审核和导出都绑定在同一个快照上，谁也不能偷偷换掉依据。

**第五步：生成内容并审查。**

用户选择某个章节，发起生成。系统会先在已经确认的资料里检索相关证据，检查资料是不是齐全。如果缺少必要的资料，系统会暂停下来，告诉用户"缺什么、为什么缺、建议怎么补"，而不是硬编内容。

资料齐全之后，系统按固定的流程生成草稿：生成内容、跑规则检查、做语义审查、有限次数地修订、保存成候选版本。所谓"候选版本"，就是它**不会自动替换**你正在编辑的内容。要不要采用，由用户明确决定。

生成过程中产生的每一次模型调用、消耗的 Token 数量、估算的费用，都会被记录下来，可以在运行详情里查看。

**第六步：审查、审核与导出。**

系统会对内容做两类检查。规则检查负责确定性的问题，例如工期数字前后不一致、项目名称写错、引用失效、还有待补内容没填。语义审查负责需要理解才能判断的问题，例如评分项有没有响应、内容是不是针对本工程、证据能不能支撑结论。

检查发现的问题带着严重程度：blocker（阻断级）、high（高）、medium（中）、low（低）。阻断级的问题不允许人工"接受风险"绕过，必须修改内容后重新检查；其他级别的问题可以处理，但必须留下处理人和理由。

最后由审核人员审核。有一条重要规则：**任何人都不能审核自己创建的内容**，管理员也不行。审核通过之后，系统才能导出"提交草稿"。如果导出之后相关数据又发生了变化，系统会让这份导出"过期"，不允许把旧文件当作当前成果使用。

把上面六步连起来，就是整个产品的价值链：

```text
招标要求 → 已确认的项目事实 → 企业资料和参考资料 → 章节内容
→ 审查发现的问题 → 人工审核 → 导出草稿
```

### 1.4 系统由哪些部分组成

这个系统由九个部分组成。下面我用"它负责什么"和"如果没有它会怎样"来解释每一部分，你现在不需要记住技术细节，只需要建立整体印象。

**前端（浏览器界面）。** 用户在浏览器里看到和操作的所有页面，例如登录页、项目列表、章节编辑器、审查页面。它负责把用户的操作发送给后端，并把结果显示出来。没有它，用户就只能用命令行操作，普通人无法使用。

**API 服务。** 它是整个系统的"前台接待员"。所有来自浏览器的请求都先到这里，它负责检查身份和权限、校验输入、调用业务逻辑、返回结果。没有它，前端不知道把请求发给谁，也无法统一控制权限。

**数据库。** 它是整个系统唯一的"事实来源"。项目、资料、要求、基准、章节版本、运行记录、审查结果全部存在这里。没有它，所有数据都无处存放，刷新页面就全没了。本项目使用 PostgreSQL，并且安装了 pgvector 扩展来支持向量检索。

**后台任务系统。** 有些工作很慢，例如解析一份三百页的 PDF、调用模型生成一章内容、导出 Word 文件。这些工作不能在用户点击按钮时同步等待，否则页面会卡住几分钟。后台任务系统负责把这些活排到队列里慢慢做，并把进度告诉用户。本项目使用 Celery 作为任务框架、Redis 作为消息中转。

**工作流引擎。** "生成一章内容"不是一步完成的，而是很多步：准备、检索、检查缺口、生成、规则检查、语义审查、修订、保存。工作流引擎负责按顺序执行这些步骤，并且支持"暂停等人"和"意外中断后从断点继续"。本项目使用 LangGraph，它类似游戏里的存档点机制。

**文档处理模块。** 它负责把 PDF 和 DOCX 读成结构化的内容块，也负责把章节内容渲染成 Word 文件。本项目使用 Docling 做解析，使用 python-docx 做导出。

**文件存储。** 原始文件、解析产物、导出的 Word 文件都保存在私有的对象存储里，不放在数据库里，也不允许公开访问。用户要下载文件时必须经过权限检查。本项目使用兼容 S3 协议的 SeaweedFS。

**模型接入层（ModelGateway）。** 所有对 AI 模型的调用都必须经过这一层。它负责统一管理超时、重试、结构校验、费用记录，并且隔离不同供应商的差异。它还有一个"模拟模式"，用确定性的假结果替代真实模型，让你在没有密钥、不花钱的情况下把整个流程跑通。

**部署与运维。** 负责把这些程序打包成容器、启动起来、监控运行状态、备份数据、在出故障时恢复。本项目使用 Docker Compose 在一台机器上运行全部服务，用 Nginx 提供 HTTPS 入口。

### 1.5 四份设计文档是什么关系

这个项目在动手之前先写了四份文档，它们各自负责不同的内容，你需要知道什么时候该查哪一份。

| 文档 | 它回答的问题 | 什么时候需要更新 |
|---|---|---|
| [开发方案.md](./开发方案.md) | 产品是什么、服务谁、第一版做什么、不做什么、分几个阶段 | 当产品范围发生变化时 |
| [开发文档.md](./开发文档.md) | 系统怎么设计、模块怎么划分、写代码要遵守哪些业务规则 | 当实现方式发生变化时 |
| [API文档.md](./API文档.md) | 系统对外提供哪些接口、每个接口的输入输出、权限和错误码 | 当对外行为发生变化时 |
| [数据库文档.md](./数据库文档.md) | 数据怎么存、有哪些表、有哪些约束、事务和迁移怎么做 | 当数据存储方式发生变化时 |

四份文档的阅读顺序建议是：先看开发方案建立整体印象，再看开发文档理解规则，最后把 API 文档和数据库文档当成工具书，需要的时候查具体章节。

如果四份文档之间出现了冲突，处理的顺序是：**先停下来，用一条 ADR 记录你最终选择了什么、为什么这样选**，然后再继续写代码。绝对不允许让代码"悄悄替你做决定"，因为那样过一段时间之后，没有人能说清楚系统到底按什么规则在运行。

### 1.6 开发过程分成六个阶段、26 个步骤

整个项目分成六个阶段，除准备阶段以外，每个阶段都对应设计文档里规划的一个开发阶段（P1 到 P5）。每个阶段内部再拆成若干步骤，一共 26 个步骤。

| 阶段 | 名称 | 包含步骤 | 这个阶段结束时你能演示什么 |
|---|---|---|---|
| 准备 | 环境、知识、业务功课 | 无编号，对应门禁 G0 | 环境检查通过，样本和 ADR 就位 |
| 阶段一 | 产品骨架 | A1 到 A8 | 能登录、建项目、传文件，后台任务能跑 |
| 阶段二 | 知识与事实底座 | B1 到 B4 | 解析、确认、基准、检索全部可追溯 |
| 阶段三 | 单章生成闭环 | C1 到 C5 | 一章内容从生成到采用，能暂停能恢复 |
| 阶段四 | 审查、审核、导出 | D1 到 D4 | 两个角色配合完成审核并导出 Word |
| 阶段五 | 上线级质量 | E1 到 E5 | 公网可演示，有评测报告和恢复演练记录 |

难度是逐步上升的。阶段一从"完成一次 Git 提交"这种不需要写代码的事情开始；阶段二开始要求多个模块互相配合；阶段三和阶段四是整个项目最难的部分，但到那个时候，你已经有了自己的代码习惯和工具链；阶段五的难度主要来自细心和坚持，概念本身并不难。

每个步骤前面都会标注难度和预计时间。二十六步都是主线内容，必须完成；步骤内部标着"增强项"的小任务可以在时间紧张时推迟，但不能删除对应的设计。

### 1.7 如果时间不够：哪些可以砍，哪些绝对不能砍

现实情况是，你可能没有办法完整投入几个月。这份手册提供了两条压缩路径（详见附录 F），但压缩有一条底线：**隔离、证据、版本、恢复和关键测试不能删除**。

为什么这五样不能删？

**隔离**指的是不同组织之间的数据不能互相看见。这是安全底线，一旦出问题就是数据泄露事故，不是功能缺陷。

**证据**指的是每一条内容和结论都要能追溯到来源。这是这个产品存在的理由，删掉它，产品就退化成普通的 AI 写作工具。

**版本**指的是所有重要内容都不可原地修改，每次修改产生新版本。这是审计和可追溯的基础，删掉它，审核就失去意义。

**恢复**指的是任务中断、进程崩溃、数据库重启之后系统还能继续工作。这是"能演示"和"能使用"的分界线。

**关键测试**指的是跨组织隔离、重复投递、断点恢复、审核条件这些负面案例的自动化测试。它们是上面四样东西的保险丝。

可以压缩的是范围：减少重点章节的数量、简化界面细节、缩小评测样本规模、减少监控面板。但每一处压缩都要在文档里写清楚"这里简化了什么、会影响什么"。

## 第 2 章 理解企业开发流程：一个功能从想法到上线

这一章不写代码，但非常重要。它让你知道"在真正的软件公司里，一个功能是怎么被做出来的"。你一个人完成这个项目时，会把整套流程都走一遍，只是每个角色都由你来扮演。

### 2.1 一个功能从想法到上线的完整旅程

我们用一个具体的功能当例子：**给项目列表增加一个"归档"按钮**。这个功能的功能设计在 [开发方案.md](./开发方案.md) 和 [API文档.md](./API文档.md) 里已经写好了，我们的任务就是把它实现出来，并发布出去。

**第一站：需求评审。**

产品文档里写着："归档由管理员执行，需要项目没有非终态运行；归档项目只读，保留下载与历史查看。"产品评审会上，大家会确认这些细节：为什么必须是管理员？因为没有结束的后台任务时归档会导致任务半途而废；归档后为什么还能看历史？因为审计和复盘需要。评审结束后，需求被写成一个 Issue，Issue 里包含验收标准。

**第二站：技术方案评审。**

开发人员看完需求，先判断技术上要改什么：数据库需要新增字段吗？（不需要，`status` 字段已经存在，只需要从 active 改成 archived。）接口需要新增吗？（需要，`POST /projects/{id}/archive`。）权限怎么控制？（只有 admin 可以。）并发怎么处理？（请求要带 `expected_lock_version`，防止两个人同时归档或者一边归档一边修改。）这些判断会在评审会上确认，必要时写一条 ADR。

**第三站：任务拆分。**

一个"归档功能"听起来不大，但仍然要拆成几个独立的小任务：后端接口与校验逻辑、数据库层不需要改动、前端按钮与二次确认弹窗、后端自动化测试、前端手工验证、更新文档。每个小任务都应该能在半天到一天内完成，并且可以单独提交。

**第四站：开发。**

开发者从主分支切出一个功能分支，名字叫 `feat/project-archive`。然后按小任务逐步实现、逐步提交。每完成一小块就运行一次测试，而不是攒到最后一起测。

**第五站：自测。**

开发者自己先跑一遍所有测试，并且手工验证：正常归档能成功；归档一个不存在或者别的组织的项目会返回 404；归档一个还有未完成任务的项目会返回 409 并且提示原因；归档之后尝试上传文件会被拒绝。这一步的目的不是"证明我能做出来"，而是"证明它在该出错的时候会出错"。

**第六站：提交 PR（Pull Request，合并请求）。**

开发者把分支推到远端仓库，创建一个 PR，并在描述里写清楚：做了什么、怎么验证的、有没有接口或数据库变更、有什么风险。即使这个项目只有你一个人，也要坚持写 PR，因为 PR 描述是你三个月后回顾这段代码的唯一线索。

**第七站：CI 门禁。**

PR 创建之后，CI（持续集成）流水线会自动运行：代码风格检查、类型检查、单元测试、集成测试、前端构建。任何一项失败，PR 都不能合并。这一步相当于"每次提交都自动做一次体检"，避免人工忘记检查。

**第八站：代码评审（Code Review）。**

另一个人（或者你换一个视角、或者让 AI 帮忙）阅读代码，检查：逻辑是否正确、边界情况是否处理、命名是否清楚、有没有安全风险、测试是否覆盖了失败路径。评审意见修改完成之后，PR 才能合并。

**第九站：合并、构建与部署。**

PR 合并到主分支后，流水线自动构建一个新的容器镜像（带版本号），然后把它部署到测试环境。部署之前先执行数据库迁移，部署之后运行冒烟测试（smoke test，即"最关键的那几条路径能不能走通"）。

**第十站：观察与复盘。**

上线之后观察一段时间：错误日志有没有增加、接口响应时间有没有变慢、后台任务有没有堆积。如果发现问题，先回滚到上一个版本，再排查原因。事情结束之后写一份简短复盘：哪里顺利、哪里卡住、下次怎么改进。

把上面十站画成一条线，就是企业里最常见的研发流程：

```text
需求评审 → 技术方案 → 拆任务 → 开发 → 自测 → PR
→ CI 门禁 → 代码评审 → 合并 → 构建镜像 → 部署
→ 冒烟测试 → 监控观察 → 出问题回滚 → 复盘
```

### 2.2 每个环节在防止什么问题

很多人觉得这些流程是"大公司的繁文缛节"。其实每一个环节都对应着一个真实的坑，都是有人踩过之后才总结出来的。

| 环节 | 它防止的问题 | 如果省略会发生什么 |
|---|---|---|
| 需求评审 | 做出来的东西不是用户要的 | 开发两周之后发现方向错了，全部返工 |
| 技术方案与 ADR | 架构反复推翻、后人不知道当时为什么这么设计 | 半年后没人敢改代码，只能重写 |
| 任务拆分 | 一次改动太大，出问题无法回滚 | 一次提交包含二十个改动，出错了不知道是哪一处 |
| 自动化测试 | 新功能把旧功能改坏 | 每次发布都要人工把所有功能重新点一遍 |
| CI 门禁 | 人工检查会遗漏 | 评审通过但测试没跑，合并后主分支直接坏掉 |
| 代码评审 | 个人盲区、风格不统一 | 明显的 bug 流到线上 |
| 迁移评审 | 上线把数据改坏 | 数据库结构变更无法回滚，恢复要靠备份 |
| 部署前备份 | 发布失败无法恢复 | 线上事故持续几个小时 |
| 监控告警 | 出问题没人知道 | 用户先发现故障，公司后知道 |
| 复盘 | 同样的坑反复踩 | 每个月都在解决同一类问题 |

在这个项目里，每一道环节都有具体的对应物。例如"需求评审"对应第 3 章的业务功课，"技术方案"对应 `docs/adr/` 里的九条记录，"自动化测试"对应每个步骤要求的测试清单，"CI 门禁"对应 A2 步骤就要搭建的流水线。

### 2.3 一个人怎么模拟整套流程

你是一个人在做这个项目，没有产品经理、没有测试工程师、没有运维同事。但这不代表你要放弃流程，你可以用下面的方式把每个角色都"演"一遍。

**用 GitHub Issues 管理需求。** 每个开发步骤开一个 Issue，标题写清楚编号和名称，例如 `[A3] 数据库、迁移与集成测试`。Issue 的正文里写三条验收标准。做完了再关掉它。这样做的意义是：你的工作有清单、有记录，不会做到一半忘了当初要做什么。

**每个步骤开一个分支。** 分支名用 `feat/a3-db-migration` 这样的格式。做完之后提 PR，即使自己合并也要走完整流程：写描述、等 CI、自查一遍再合并。这样做的意义是：主分支始终保持可用，任何时候都能回滚。

**每一次 PR 都写完整描述。** 描述里至少包含四件事：做了什么、怎么验证的、有没有接口或数据库变更、有什么风险或者没做完的部分。可以参考附录 C 的模板。

**让 CI 成为你的"第二双眼睛"。** 从 A2 步骤开始就把最小流水线搭起来，之后每加一个功能就加对应的检查。你的目标是：任何一次合并之前，机器已经帮你把该跑的都跑了一遍。

**每周做一次迭代评审。** 每周五给自己留一个小时，对着屏幕演示本周完成的功能，顺便录一段五分钟的视频存档。演示不出来的功能，就不算完成。这个习惯会逼你把功能做成"真的能用"，而不是"看起来写完了"。

**每月做一次复盘。** 用半页纸回答四个问题：这个月完成了什么？卡在哪里？返工的原因是什么？下个月要调整什么？复盘不是自我批评，而是为了让下个月少走弯路。

### 2.4 为什么不能只靠手点：测试分层

你可能会想："我自己点一遍不就知道功能好不好用了吗？"问题是，项目做到后面，功能会越来越多，每次改动都手工重测一遍是不可能的。而且人工测试会疲劳、会遗漏。所以我们要用自动化的方式来代替重复劳动。

不同层次的测试，成本和价值不一样。这个项目采用下面五层结构：

| 测试类型 | 测试什么 | 这个项目里的例子 | 运行速度 | 数量 |
|---|---|---|---|---|
| 单元测试 | 不依赖数据库和网络的纯逻辑 | 运行状态机、预算计算、导出条件判断 | 毫秒级 | 最多 |
| 集成测试 | 真实数据库、事务、权限 | 跨组织读写被拒绝、并发保存只有一个成功 | 秒级 | 中等 |
| 合同测试 | 与外部系统约定的接口行为 | 模型超时、限流、返回结构错误 | 秒级 | 少量但必须有 |
| 端到端测试 | 从浏览器完整走一遍主流程 | 登录、建项目、生成、审核、导出 | 分钟级 | 三到五条主路径 |
| 人工评测 | 内容质量这类机器难判断的东西 | 抽取准确率、引用是否支持结论 | 小时级 | 每个版本一次 |

原则是：**能用便宜的方式验证，就不要用昂贵的方式**。一个规则逻辑能用单元测试覆盖，就不要写端到端测试；但每一条核心业务路径，必须至少有一条集成测试或者端到端测试兜底。

### 2.5 "完成"的五条标准

在这个项目里，"做完了"不是一种感觉，而是一个可以被检查的标准。每个步骤结束时，都要用下面五条来检验：

**第一条：能演示。** 你能当场用命令或者浏览器演示这个功能，而不是说"应该没问题"。如果演示不出来，就是没完成。

**第二条：有测试。** 至少有一个自动化测试覆盖了主要路径；如果这个功能有失败分支，失败分支也要有测试。测试必须能被别人重跑。

**第三条：文档同步。** 如果这次改动影响了对外接口、数据库结构或者重要决策，对应的文档已经更新。文档不是写给别人的，是写给三个月后的你自己的。

**第四条：有提交记录。** 改动通过规范的小提交进入仓库，提交信息能让人看懂改了什么、为什么改。

**第五条：失败有交代。** 功能出错时，用户能看到清楚的提示，系统能记录明确的错误码，不会静默失败，也不会把失败伪装成成功。

### 2.6 做完这个项目，你会留下哪些证据

这个项目本身是求职作品。作品的可信度不只来自"能跑起来"，更来自你能拿出哪些过程证据。

做完之后，你应该拥有下面这些东西：

- 一个可以克隆、可以按 README 启动的代码仓库。
- 一条条可以点开的 PR 记录，以及每条 PR 上绿色的 CI 检查结果。
- `docs/adr/` 目录里的架构决策记录，说明你为什么做了这些技术选择。
- 自动化测试的结果，包括单元、集成和端到端测试。
- `evaluation/reports/` 里的评测报告，说明系统在什么样本上达到什么水平，还有哪些失败案例。
- `docs/drills/` 里的故障演练和恢复记录。
- 一份五到十分钟的业务演示视频。
- 一份诚实的说明：哪些功能已实现、哪些只是预留、哪些指标还没有测量。

在面试里，你能拿出这些材料，和只能拿出一个"我做了个 AI 项目"的说法，是完全不同的两种可信度。

### 3.2 一步一步安装并验证环境

下面每一步都按照"做什么、为什么、怎么验证、失败怎么办"来写。请按顺序完成，不要跳步。

#### 3.2.1 安装一个 Node 版本管理器

**做什么**：安装 fnm（推荐）或者 nvm-windows，然后安装并使用 Node.js 22。

**为什么**：Node.js 是运行前端开发工具和构建前端代码的程序。项目要求 22 版本，而你的电脑上是 24 版本。版本管理器可以让你随时切换，不会互相干扰。

**怎么做**：安装 fnm 之后，打开一个新的 PowerShell 窗口，运行：

```powershell
fnm install 22
fnm use 22
node -v
```

如果你使用 nvm-windows，它通常要求写完整的版本号，先用 `nvm list available` 找到 22 系列最新的补丁版本，再执行 `nvm install 完整版本号` 和 `nvm use 完整版本号`。

**怎么验证**：`node -v` 的输出应该以 `v22` 开头。然后在项目根目录创建一个名为 `.nvmrc` 的文件，内容写一行 `22`。这样以后别人拿到你的项目，也能知道应该用哪个 Node 版本。

**失败怎么办**：如果命令不存在，说明安装之后没有重新打开终端，或者环境变量没有生效。关掉所有 PowerShell 窗口重新打开一次；还不行就重新读一遍安装说明。

#### 3.2.2 用 uv 安装 Python 3.12

**做什么**：运行下面的命令，让 uv 帮你下载并安装一个独立的 Python 3.12。

```powershell
uv python install 3.12
uv python list
```

**为什么**：uv 是这个项目使用的 Python 环境管理工具。它同时负责三件事：安装 Python 版本、创建项目专用的虚拟环境、安装和管理第三方库。它比手工下载安装包、手工配置环境变量简单得多。

**怎么验证**：`uv python list` 的输出里应该能看到 3.12 的版本号。

**失败怎么办**：这需要从网络下载，如果速度很慢或者失败，先检查网络；公司网络可能需要配置代理。

#### 3.2.3 验证 Docker

**做什么**：运行下面两条命令。

```powershell
docker run --rm hello-world
docker compose version
```

**为什么**：Docker 是用来运行数据库、Redis、文件存储这些基础服务的。用容器运行它们的好处是：不需要在你电脑上安装这些软件，也不需要担心配置被搞乱；项目提供的配置文件会在需要时启动它们。

**怎么验证**：第一条命令会下载一个极小的镜像并输出一段欢迎信息；第二条命令会输出版本号。

**失败怎么办**：Windows 上最常见的原因是 Docker Desktop 没有启动，或者没有启用 WSL2 后端。先确认 Docker Desktop 正在运行；如果提示 WSL 相关错误，按照 Docker Desktop 的提示安装或更新 WSL。

#### 3.2.4 配置 Git 身份

**做什么**：运行下面两条命令，把名字和邮箱换成你自己的。

```powershell
git config --global user.name "你的名字"
git config --global user.email "你的邮箱"
git config --global core.autocrlf false
```

**为什么**：每次提交代码时，Git 会把作者信息写进历史记录，方便以后追溯。第三条命令是关掉 Windows 下的自动换行转换，让换行符的处理方式在所有系统上保持一致。

**怎么验证**：运行 `git config --global --list`，应该能看到刚才设置的三项。

#### 3.2.5 注册 GitHub 并建立一个练习仓库

**做什么**：注册 GitHub 账号，新建一个仓库，名字随意，例如 `git-practice`。然后在本地创建一个对应目录，练习 3.6 节的 Git 操作。

**为什么**：GitHub 是代码托管平台。你的项目代码、分支、PR 和 CI 记录都会放在这里。练习仓库的作用是让你在"弄坏了也不心疼"的环境里熟悉 Git，避免在正式仓库里反复试错。

**怎么验证**：能成功执行 `git push`，在网页上能看到你推上去的文件。

### 3.5 业务功课：先想清楚，再写代码

很多人拿到项目就急着写代码，结果写到一半发现方向不对。企业里的做法是先做"需求澄清"和"范围锁定"，对应到我们的项目就是 P0 阶段。这一节你不写代码，但要产出几份文件。

#### 3.5.1 锁定工程类型和重点章节

**做什么**：从常见的工程类型里选择一个，例如"市政道路工程"或者"公共建筑机电安装工程"。然后从技术标的章节里选择三到五类重点章节，建议从施工方案、进度安排、质量保证、安全文明施工、资源配置里选。

**为什么**：如果不锁定范围，你会面对成百上千种工程类型和几十个章节，每个都做一点，每个都做不深。锁定范围之后，你的样本、提示词、评测都围绕同一个场景展开，质量才有保证。

**怎么完成**：把这些决定写进 ADR，例如 `0002-锁定市政道路工程.md`。ADR 的格式见附录 B，内容写清楚"选了哪个、为什么选它、放弃了哪些、有什么影响"。

#### 3.5.2 准备业务样本

**做什么**：准备至少四份样本文件：一份招标文件（最好包含评分办法）、一份企业资料、一份历史标书、一份技术参考资料。

**为什么**：后面所有功能都要用真实文件来测试。如果只有一份随便找的文档，你无法判断解析、抽取、检索到底做得好不好。

**有一条必须遵守的纪律**：只能使用已经获授权使用、或者已经脱敏的资料。如果你手上没有合适的资料，就用自己编造的模拟样本。使用模拟样本不丢人，使用未授权的真实资料才是事故。

**怎么完成**：在 `evaluation/manifests/` 目录下创建一个清单文件，记录每份样本的编号、类型、工程类型、授权状态、脱敏方式、文件哈希值，以及它属于调试集还是保留集。清单的格式可以用 Markdown 表格，也可以用 JSON，重要的是信息齐全。

#### 3.5.3 补齐架构决策记录

**做什么**：在 `docs/adr/` 目录下，把九条关键决策各写成一份记录。这九条决策是：为什么用模块化单体、为什么只接一个模型供应商、为什么把词项检索和向量检索放在同一个数据库、为什么 AI 生成的内容不自动采用、为什么需要基准快照、Celery 和 LangGraph 各自负责什么、数据库权限边界怎么划、为什么需要模拟模式、为什么第一版只做单机部署。

**为什么**：这九条决策覆盖了这个项目最重要的技术取舍。写它们的过程，就是你真正理解这个系统设计的过程；写完它们，你在面试里被问"为什么这么做"时，就能给出有依据的回答，而不是背课文。

**怎么完成**：每条 ADR 半页到一页，包含背景、决策、备选方案、后果四个部分。附录 B 有模板。

#### 3.5.4 把主流程画一遍

**做什么**：打开 [开发方案.md](./开发方案.md) 第 4.2 节，把里面的主流程用自己的话抄写一遍，每一步写一两句解释。

**为什么**：亲手写一遍和用眼睛看一遍，理解程度完全不同。这个练习能帮你建立"我做的每个功能在整条链路里的位置"这种整体感，避免后面变成"照着清单打勾，但不知道为什么"。

### 3.6 Git 实操练习

在开始正式的项目之前，先在练习仓库里把 Git 的基本操作做一遍。下面每一步我都会解释"发生了什么"，而不只是给命令。

```powershell
cd D:\proj\git-practice
git init
```

`git init` 的作用是把当前目录变成一个 Git 仓库，也就是开始记录这个目录里所有文件的变化。

```powershell
"第一行内容" | Out-File -Encoding utf8 hello.txt
git status
```

你创建了一个文件，`git status` 会告诉你有一个"未被跟踪的文件"。所谓未被跟踪，就是 Git 发现这个文件存在，但还没有把它纳入版本记录。

```powershell
git add hello.txt
git commit -m "docs: 添加 hello 文件"
git log --oneline
```

`git add` 把文件放进"暂存区"，意思是"我确认要记录这个文件当前的样子"；`git commit` 把暂存区的内容正式保存成一个历史版本。`git log` 可以看到刚才这条记录。

接下来练习分支：

```powershell
git branch feature/learn
git switch feature/learn
"第二行内容" | Out-File -Encoding utf8 hello.txt -Append
git add hello.txt
git commit -m "docs: 在分支上添加第二行"
git switch main
git merge feature/learn
```

分支的作用是让你在不影响主线的情况下做实验。`git merge` 把分支上的改动合并回主线。

最后，故意制造一次冲突：新建两个分支，分别修改同一个文件的同一行，然后合并。Git 会提示冲突，你需要在文件里手工选择保留哪一行，然后重新 `git add` 和 `git commit`。**冲突不是事故，而是正常现象。** 会解决冲突，是从"会用 Git"到"不怕 Git"的分水岭。

### A1 仓库与第一次提交

**难度**：一星（入门）　**预计时间**：3 到 5 小时

#### 这一步要解决什么问题

写代码之前，先要给代码找一个"家"，并且把这个家的规矩定下来。这一步结束后，你会拥有一个目录清晰、规则明确的代码仓库，并且完成第一次提交。提交的意思是：把你的文件正式记录进版本历史，从此以后每一次修改都可以追溯、可以回退。

这一步不需要写任何程序代码，但它决定了你后面二十多个步骤的工作方式。

#### 动手之前，先弄懂几个词

**仓库（Repository）**：被 Git 管理的项目目录。Git 会记录这个目录里所有文件的变化历史。仓库可以只存在于你的电脑上，也可以同步到 GitHub 这样的远程平台。

**提交（Commit）**：一次"存档"。你修改了一些文件，确认无误之后，把它们打包记录成一个历史版本。每个提交都带一条说明信息，例如"添加数据库迁移脚本"。

**分支（Branch）**：一条独立的开发线。你可以在分支上做实验，做好之后再合并回主线。主线通常叫 `main`。

**远程仓库（Remote）**：托管在 GitHub 上的副本。它让代码有备份，也让你可以在网页上查看提交记录、创建 PR、运行 CI。

**`.gitignore` 文件**：一份清单，告诉 Git"这些文件不要记录"。例如虚拟环境目录、密钥文件、日志文件都不应该进入版本历史。

**README 文件**：仓库的说明书，放在最外层。别人（包括三个月后的你）打开仓库第一眼看到的就是它。

#### 具体怎么做

**第一步：补全 `.gitignore` 文件。**

你现在的项目里已经有一个 `.gitignore`，但是内容是空的。请把它补成下面这样，每一类的含义我都写在注释里：

```gitignore
# Python 相关：虚拟环境、缓存、编译产物
.venv/
__pycache__/
*.pyc
.pytest_cache/
.mypy_cache/
.ruff_cache/

# 前端相关：依赖目录和构建产物
node_modules/
dist/
coverage/

# 环境与数据：密钥文件、日志、本地数据
.env
*.log
var/

# 编辑器与系统：个人配置和系统临时文件
.idea/
Thumbs.db
.DS_Store
```

关于 `.vscode/` 目录有一个小小的取舍：个人偏好设置放在这里的话可以忽略；如果是全项目统一的设置（例如"保存时自动格式化"），应该提交到仓库，让所有人一致。建议的做法是：只把统一的 `.vscode/settings.json` 提交上去，其余忽略。

**第二步：写 README。**

创建或改写 `README.md`，内容至少包含下面几块。现在很多内容可以先写"计划中"，以后随着开发逐步补全：

```markdown
# 工程标书 AI Harness Agent

面向工程技术标的 AI 撰写工作台，具备证据追溯与人工审核能力。

## 项目状态
设计完成，正在实现中。

## 文档
- 开发方案：链接
- 开发文档：链接
- API 文档：链接
- 数据库文档：链接

## 技术栈
后端：Python 3.12、FastAPI、PostgreSQL、Redis、Celery
前端：React、TypeScript、Vite
部署：Docker Compose、Nginx

## 本地启动
（随着开发进度补充）
```

**第三步：建立目录骨架。**

按照 [开发文档.md](./开发文档.md) 第 2.2 节创建下面这些目录。空目录在 Git 里不会被记录，所以每个目录里放一个占位文件（例如 `.gitkeep`）或者一个简短的说明文件：

```text
backend/            后端代码
frontend/           前端代码
deploy/             部署配置，例如 Docker Compose
scripts/            各种辅助脚本，例如初始化、备份
docs/adr/           架构决策记录
docs/notes/         学习笔记和复盘记录
docs/drills/        故障演练记录
evaluation/manifests/   评测样本清单
evaluation/cases/       评测样本和问题
evaluation/reports/     评测报告
.github/workflows/  CI 流水线配置
```

**第四步：完成第一次提交。**

```powershell
git add -A
git commit -m "chore: 建立仓库骨架与文档基线"
git branch -M main
git remote add origin <你的仓库地址>
git push -u origin main
```

这几条命令依次做的事情是：把所有改动放进暂存区；生成一次提交；把当前分支改名为 `main`；把本地仓库和 GitHub 上的远程仓库关联起来；把代码推上去。

**第五步：开启分支保护。**

在 GitHub 仓库的设置里，为 `main` 分支开启保护规则：要求通过 PR 才能合并，要求 CI 检查通过才能合并。即使只有你一个人开发，这个设置也能防止你随手把没测试的代码推到主分支上。

#### 怎么算做完了

- [ ] 运行 `git log --oneline`，能看到至少一条提交记录。
- [ ] 运行 `git status`，输出是"工作区干净"，没有莫名其妙的多余文件。
- [ ] 仓库里看不到 `.venv/`、`node_modules/`、`.env` 这类不应该提交的东西。
- [ ] README 能让一个陌生人三十秒内知道这个项目是做什么的。
- [ ] GitHub 上能看到你的代码，`main` 分支保护已经开启。

#### 常见问题和提醒

**最常见的错误是先提交、后写 `.gitignore`。** 如果垃圾文件已经被提交过，光写 `.gitignore` 是不够的，还需要用 `git rm --cached 文件名` 把它从版本记录里移除。

**第二个常见错误是把密钥写进文档或者代码。** 一旦推送到远端，就要当作已经泄露处理，正确做法是立刻去对应平台更换密钥。

**第三个提醒是关于 `.idea/` 目录。** 这是 JetBrains 系列编辑器的个人配置，通常应该忽略。如果你和团队共用运行配置，可以单独把配置目录提交，但要在 README 里说明原因。

#### 这一步和企业开发的关系

在公司里，这一步叫"项目初始化"，通常由项目的第一个开发者完成。真实环境里还会配置更多东西，例如代码所有权声明（CODEOWNERS，规定哪些目录必须由谁评审）、提交签名、仓库权限分级。但核心逻辑和你现在做的一样：先定规矩，再写代码。

### A2 后端最小 API 与质量工具链

**难度**：一星（入门）　**预计时间**：8 到 12 小时

#### 这一步要解决什么问题

这一步要搭出后端工程，让它能启动、能接受一个最简单的网络请求，并且能自动运行代码检查和测试。完成后，你在浏览器里访问一个地址，会看到服务器返回的 JSON 数据；同时你有了三条自动化的"体检线"：代码风格检查、类型检查、单元测试。

这里写的接口叫"健康检查"，它的作用是告诉外界"这个服务还活着"。后面所有的业务接口都会长在同一个工程里。

#### 动手之前，先弄懂几个词

**后端**：运行在服务器上、用户看不见的那部分程序。它负责处理业务逻辑、读写数据库、返回数据。

**API（应用程序接口）**：后端对外提供的一组能力。前端通过调用 API 来获取数据或者提交操作。

**端点（Endpoint）**：API 里的一个具体地址。例如 `GET /health/live` 就是一个端点，它表示"用 GET 方式访问 /health/live 这个地址"。

**uvicorn**：运行 Python Web 程序的服务器。你写好的代码需要由它启动起来，才能对外提供服务。

**依赖**：你的项目需要用到的第三方代码库。例如 FastAPI 就是一个依赖，uv 负责帮你下载和管理它们。

**虚拟环境**：每个项目独立的 Python 运行环境。它的作用是避免不同项目的依赖版本互相冲突。

**代码风格检查（Lint）**：自动检查代码里有没有明显的风格问题和低级错误，例如未使用的变量、错误的导入顺序。

**类型检查**：检查代码里的类型标注是否一致，例如一个函数声明返回数字，实际上返回了文字，类型检查会提前报警。

**单元测试**：针对一小段逻辑写的自动检查。运行一次只需要几毫秒，可以频繁执行。

**CI（持续集成）**：每次提交代码时自动运行检查的流水线。它相当于一个不知疲倦的质检员。

#### 具体怎么做

**第一步：初始化后端项目。**

```powershell
cd backend
uv init --python 3.12
uv add fastapi "uvicorn[standard]" pydantic-settings
uv add --dev pytest httpx ruff mypy
```

第一条命令在当前目录初始化一个 Python 项目，并指定使用 3.12 版本；第二条命令安装运行需要的依赖；第三条命令安装只在开发时使用的依赖（测试框架、检查工具）。

**第二步：写第一个程序文件 `app/main.py`。**

代码大致长这样，你可以照着写，然后逐行理解：

```python
from fastapi import FastAPI

app = FastAPI(title="工程标书 AI Harness Agent")


@app.get("/health/live")
def live() -> dict[str, str]:
    return {"status": "ok"}
```

这段代码做的事情是：创建一个应用对象；注册一个地址为 `/health/live` 的接口；当有人访问时返回一段 JSON。

有些内容这里故意没有做，例如没有检查数据库连接。原因是健康检查分两种：`live` 只表示"进程活着"，`ready` 才表示"依赖都正常"。具体的规则写在 [API文档.md](./API文档.md) 第 13 节。

**第三步：把配置独立出来。**

创建 `app/core/config.py`，用来读取环境变量。你暂时可以只定义几个字段，例如运行环境名称、数据库地址、模型模式。配套创建一个 `.env.example` 文件，里面列出所有配置项的名字和示例值，但**不要写真实的密钥**。

**第四步：写第一个测试。**

创建 `tests/unit/test_health.py`，内容大致如下：

```python
from fastapi.testclient import TestClient

from app.main import app

client = TestClient(app)


def test_live_returns_ok() -> None:
    response = client.get("/health/live")
    assert response.status_code == 200
    assert response.json() == {"status": "ok"}
```

这个测试做的事情是：在没有真正启动服务器的情况下，模拟发送一次请求，然后检查状态码和返回内容是否符合预期。

**第五步：配置质量工具和启动命令。**

在 `pyproject.toml` 里配置 ruff 和 mypy 的检查范围。然后在 `scripts/` 目录里写一个启动脚本，内容类似：

```powershell
uv run uvicorn app.main:app --reload
```

`--reload` 表示修改代码后自动重启服务，方便开发。

**第六步：搭建最小 CI。**

在 `.github/workflows/ci.yml` 里配置流水线：安装 uv、安装依赖、运行 `ruff check`、运行 `mypy app`、运行 `pytest`。推送一个测试用的 PR，确认 CI 真的会跑起来。

#### 怎么算做完了

- [ ] 运行 `uv run uvicorn app.main:app --reload`，然后用浏览器访问 `/health/live`，能看到返回的 JSON。
- [ ] 运行 `uv run pytest -q`，测试通过。
- [ ] 运行 `uv run ruff check .` 和 `uv run mypy app`，没有报错。
- [ ] 在 GitHub 上创建一个 PR，CI 自动运行并且显示绿色通过。
- [ ] `.env.example` 里没有任何真实密钥。
- [ ] 你能解释为什么 `live` 检查不查数据库，而 `ready` 检查要查。

#### 常见问题和提醒

**如果提示找不到模块**，最常见的原因是命令没有通过 `uv run` 执行，导致用到的是系统里另一个 Python 环境。解决办法是统一用 `uv run` 前缀。

**如果 mypy 报了一堆错**，不要直接把检查关掉。正确的做法是先只检查 `app` 目录，然后逐步补充类型标注，让错误一点点减少。

**如果 CI 只在主分支运行**，说明触发条件配置错了。应该在每次创建 PR 时都运行，这样才能在合并之前拦住问题。

#### 这一步和企业开发的关系

这一步在企业里叫"搭建工程脚手架"。规范的做法是：把代码风格检查、类型检查、测试和 CI 一次性配好，后面所有开发者直接沿用。这样能避免"每个人的代码风格都不一样，评审时一半时间在争论格式"这种低效情况。

### A3 数据库、迁移与集成测试

**难度**：二星　**预计时间**：10 到 14 小时

#### 这一步要解决什么问题

到目前为止，你的程序还没有任何持久化存储，重启就什么都不剩。这一步要让数据库真正跑起来，并且立下一个规矩：**所有表结构的变化都必须通过迁移脚本来完成，禁止手工修改数据库。**

迁移脚本的作用，类似给数据库做改造的施工图。它不仅记录"现在是什么样"，还记录"从上一个版本怎么变成现在这个版本"，所以任何一个空数据库都能通过依次执行迁移，变成和开发环境完全一致的结构。

#### 动手之前，先弄懂几个词

**关系型数据库**：用"表"来组织数据的数据库。每张表有固定的列，每一行是一条记录。本项目使用 PostgreSQL。

**容器**：一种轻量级的"打包运行环境"。你可以把它理解成一个专门用来运行某个软件的盒子。数据库装在盒子里，不污染你的电脑系统。

**镜像**：容器的模板。例如 `pgvector/pgvector:pg17` 是一个已经装好 PostgreSQL 17 和向量插件的镜像。

**数据卷**：挂在容器外面的存储目录。容器可以随时删除重建，但数据卷里的数据会保留，所以数据库文件要放在数据卷里。

**迁移（Migration）**：一段描述数据库结构变化的脚本，例如"新建三张表"或者"给某张表增加一列"。

**ORM**：把 Python 对象和数据库表对应起来的工具。本项目使用 SQLAlchemy，它让你可以用 Python 代码描述表结构。

**集成测试**：需要真实依赖（例如真实数据库）参与的测试。它比单元测试慢，但能验证事务、约束、权限这些只有真实数据库才能验证的行为。

#### 具体怎么做

**第一步：编写开发用的容器配置文件。**

在 `deploy/compose.yaml` 里先加入两个服务：PostgreSQL 和 Redis。内容可以参考下面的写法，但镜像版本要以 [开发文档.md](./开发文档.md) 第 2.1 节的基线为准：

```yaml
services:
  postgres:
    image: pgvector/pgvector:pg17
    environment:
      POSTGRES_USER: harness
      POSTGRES_PASSWORD: dev_only_password
      POSTGRES_DB: harness
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U harness"]
      interval: 5s
      timeout: 3s
      retries: 10

  redis:
    image: redis:7
    command: ["redis-server", "--appendonly", "yes"]
    ports:
      - "6379:6379"
    volumes:
      - redisdata:/data

volumes:
  pgdata:
  redisdata:
```

文件存储服务（SeaweedFS）到 B1 步骤再加进来。这样安排的原因是：一次只引入一个新东西，出问题的时候更容易定位。

**第二步：启动并验证。**

```powershell
docker compose -f deploy/compose.yaml up -d
docker compose -f deploy/compose.yaml ps
docker compose -f deploy/compose.yaml logs postgres
```

这三条命令分别负责启动服务、查看状态、查看数据库日志。你要看到数据库的状态是"健康"。然后重启一次电脑级别的操作（例如重新执行 `up -d`），确认数据卷里的数据还在。

**第三步：接入 SQLAlchemy 和 Alembic。**

```powershell
uv add sqlalchemy "psycopg[binary]" alembic
uv run alembic init migrations
```

第一条命令安装数据库工具；第二条命令生成迁移工具的目录结构。生成之后，你需要修改 `alembic.ini` 和 `migrations/env.py`，让迁移工具知道数据库地址在哪里、表结构定义在哪里。

这里有一个重要的选择需要说明：**本项目先使用同步版本的数据库访问方式，不使用异步版本。** 原因是这个项目的并发量很小（目标是二十个用户级别），同步代码更容易调试，和后台任务框架的配合也更自然。异步化属于后期优化，必须由性能测试证明确实有收益之后再改。这个决定值得写进一条 ADR。

**第四步：写第一个迁移。**

第一个迁移负责创建身份相关的三张表：组织表、用户表、会话表。字段要严格对照 [数据库文档.md](./数据库文档.md) 第 5 节，包括字段类型、是否允许为空、唯一约束、检查约束和默认值。

建议的做法是：先在 `app/modules/identity/` 下用 SQLAlchemy 定义模型，然后运行自动生成迁移的命令，**再逐行人工检查生成的迁移脚本**：

```powershell
uv run alembic revision --autogenerate -m "0001 identity"
uv run alembic upgrade head
```

自动生成的脚本经常需要调整，例如默认值、索引、约束可能不完整。所以"人工检查"这一步不能省。

**第五步：写第一个集成测试。**

在 `tests/integration/` 下写一个测试，连接真实的测试数据库，插入两个组织和各自的用户，验证"同一个组织内邮箱不能重复""不同组织可以用相同的邮箱"这两条约束。

注意：测试使用的数据库要和开发数据库分开，例如单独建一个 `harness_test` 数据库，每个测试结束后清理数据。**绝对不要对着开发数据库跑测试**，否则你辛苦准备的数据会被清空。

**第六步：把集成测试接进 CI。**

在 GitHub Actions 的配置里加上 PostgreSQL 服务，让流水线在运行测试之前先启动一个数据库容器。这一步做完，你的 CI 就能自动验证数据库相关的代码了。

#### 怎么算做完了

- [ ] 运行 `docker compose up -d` 之后，数据库和 Redis 的状态都是健康。
- [ ] 重启服务之后，之前写入的数据依然存在。
- [ ] 在一个空数据库上执行 `alembic upgrade head`，可以一次成功建出所有表。
- [ ] 能执行 `alembic downgrade -1` 回退一个版本，再执行升级命令回到最新版本。
- [ ] 集成测试通过，并且测试前后的开发数据库数据没有变化。
- [ ] 你亲手核对过迁移脚本和 [数据库文档.md](./数据库文档.md) 第 5 节，字段没有遗漏。
- [ ] 你能说出"为什么迁移脚本必须提交到仓库，而不能手工改数据库"。

#### 常见问题和提醒

**第一个大坑是用 SQLite 代替 PostgreSQL 做开发。** 这个项目依赖行级安全、向量类型、全文检索等 PostgreSQL 特性，SQLite 根本不支持。用 SQLite 会得到一个"在本地能跑、一上真数据库就崩"的假象。

**第二个大坑是手工改表结构。** 用数据库客户端直接加一列，看起来很快，但迁移脚本里没有这个变化，其他人的环境和线上环境都不会有这一列，最终会出现"代码里用了这个字段，线上却没有"的事故。

**第三个坑是测试之间互相污染。** 两个测试用了同一份数据，运行顺序不同结果就不同。解决办法是每个测试用独立事务并在结束时回滚，或者每个测试使用独立的数据集合。

#### 这一步和企业开发的关系

在真实公司里，数据库迁移是要经过评审的。评审会检查：这个变化会不会锁表、能不能回滚、对现有数据有什么影响、发布时要不要分步骤执行。你在这个步骤里养成的习惯——先写迁移、再人工检查、在空库上验证升级、在测试环境演练——就是这套评审的基础。

### A4 登录与会话

**难度**：二星　**预计时间**：12 到 16 小时

#### 这一步要解决什么问题

系统要知道"现在是谁在操作"。用户提交组织标识、邮箱和密码，系统验证通过之后，给他发一张"通行证"。之后用户每次请求都带着这张通行证，系统就能识别他的身份、所属组织和角色。

这一步是整个系统安全的第一道门，所以除了正常路径，还要认真处理各种异常路径：密码错了怎么办、连续错很多次怎么办、通行证过期怎么办、别人伪造请求怎么办。

#### 动手之前，先弄懂几个词

**认证（Authentication）**：确认"你是谁"。登录就是认证过程。

**会话（Session）**：认证通过之后，服务器记住你的状态。你可以把它理解成一张有时效的通行证。

**Cookie**：浏览器自动保存并在每次请求时带上的一小段数据。我们把会话凭证放在 Cookie 里，并设置成只能由服务器读取，JavaScript 读不到，这样能降低被恶意脚本窃取的风险。

**CSRF（跨站请求伪造）**：一种攻击方式。攻击者诱导你点击一个链接，借你已登录的身份去执行操作。防御方法是：写操作除了带上 Cookie，还要带上一个只有本站页面能拿到的令牌。

**哈希（Hash）**：把一段数据变成固定长度的另一段数据，而且无法反推原文。密码和会话凭证在数据库里都只存哈希，不存明文。这样即使数据库泄露，攻击者也拿不到可直接使用的密码。

**防账号枚举**：如果系统对"账号不存在"和"密码错误"返回不同的提示，攻击者就能利用这一点逐个试出哪些邮箱是注册过的。正确做法是两种情况返回完全相同的提示。

#### 具体怎么做

**第一步：实现密码哈希。**

安装 `argon2-cffi`，用它生成 Argon2id 格式的密码哈希。写一个测试来证明：同一个密码两次生成的哈希结果不同；用正确的密码可以验证通过；用错误的密码验证失败。

**第二步：实现会话。**

会话表的结构已经在 A3 创建好了。现在要写逻辑：用户登录成功后，生成一段随机字符串作为会话凭证；把它的哈希值存进数据库；同时把原始凭证通过 Cookie 发给浏览器。原始凭证永远不落库。

Cookie 的设置要符合三个要求：`HttpOnly` 让 JavaScript 读不到；开发环境不要求 HTTPS、生产环境要求 `Secure`；`SameSite=Lax` 防止跨站请求自动带上它。默认有效期是十二小时。

**第三步：实现 CSRF 令牌。**

用配置里的签名密钥和会话凭证计算出 CSRF 令牌。登录成功后把令牌返回给前端，同时也保存在服务端会话记录里。之后所有写操作（POST、PATCH、DELETE）都必须带上这个令牌，服务端比对一致才执行。

**第四步：实现四个接口。**

按照 [API文档.md](./API文档.md) 第 4 节实现：登录、查询当前用户、登出、修改密码。注意修改密码之后要撤销其他所有会话，这样别人之前偷到的凭证就失效了。

**第五步：处理各种失败情况。**

连续五次登录失败，锁定该账号十五分钟；账号不存在和密码错误返回同一条提示；未登录访问受保护接口返回"会话已过期"；首次登录但还没修改临时密码的用户，除查询信息、登出、修改密码之外的操作返回"需要先修改密码"。

**第六步：写一个初始化脚本。**

在 `scripts/` 里写一个脚本，用来创建演示用的组织和两个账号：一个编写者、一个审核者。密码从环境变量里读取，不要写死在脚本里，更不要提交到仓库。

#### 怎么算做完了

- [ ] 用正确的账号密码登录，能拿到会话凭证和 CSRF 令牌。
- [ ] 用错误的密码登录，提示信息与"账号不存在"完全一致。
- [ ] 连续失败五次之后，账号被锁定，再登录会被拒绝并提示剩余时间。
- [ ] 不带 CSRF 令牌的写请求被拒绝。
- [ ] 会话过期之后访问受保护接口，返回明确提示。
- [ ] 未修改临时密码的用户访问业务接口，返回"需要先修改密码"。
- [ ] 直接用数据库查询，确认里面找不到明文密码，也找不到原始的会话凭证。

#### 常见问题和提醒

**不要把会话凭证存进浏览器的 localStorage。** 很多教程会这么教，但那样一旦页面上有恶意脚本，凭证就会被偷走。正确做法是用 HttpOnly Cookie，前端代码根本接触不到凭证内容。

**不要为了省事把 CSRF 校验跳过。** 有人会觉得"这是内部系统，不用管"。实际上公司内网被钓鱼攻击的案例非常常见，而且后补这个校验的成本远高于一开始就做好。

**登录失败的原因不要写得太具体。** "该邮箱未注册"这种提示看似友好，实际上是在帮攻击者确认账号是否存在。

#### 这一步和企业开发的关系

认证是几乎所有安全评审的第一关。密码怎么存、会话怎么管、失败怎么提示、登录要不要限流，都是标准检查项。你在这一步养成的习惯，可以直接用在你以后做的任何系统上。

### A5 多租户隔离与权限

**难度**：三星　**预计时间**：14 到 20 小时

#### 这一步要解决什么问题

这个系统要同时服务多家企业（我们称之为"租户"或者"组织"）。甲公司的项目资料，绝不能让乙公司看到。仅仅依靠"写查询的时候记得加一个过滤条件"是不够的，因为人总会犯错。这一步要在数据库层面建立硬性约束：即使程序写错了 SQL，也读不到别的组织的数据。

#### 动手之前，先弄懂几个词

**租户（Tenant）**：使用同一个系统的不同客户组织。多租户就是"一套系统服务多家客户"。

**RLS（行级安全）**：PostgreSQL 提供的一种机制。它可以在表上定义规则，让不同连接只能看到符合规则的行。对我们来说，规则就是"只能看到自己组织的数据"。

**数据库角色**：数据库里的身份，不同的身份有不同的权限。我们要创建几个职责不同的角色，而不是所有程序都用同一个超级管理员账号连数据库。

**最小权限原则**：每个角色只拥有完成自己工作所需的最小权限。负责认证的角色不应该能读业务内容，负责调度的角色不应该能读用户数据。

**连接池**：程序启动时建立的一批数据库连接，重复使用以提高效率。连接被反复借出和归还，所以设置租户上下文时必须用"事务级"的方式，否则上一个请求的租户信息会留在连接里，污染下一个请求。

#### 具体怎么做

**第一步：创建数据库角色。**

按照 [数据库文档.md](./数据库文档.md) 第 2.3 节创建这些角色：迁移角色（只负责执行迁移）、业务角色（受行级安全约束）、认证角色（只碰账号和会话）、调度角色（只碰待投递表）。它们分别使用不同的连接。连接地址写在配置里，不允许互相借用。

**第二步：给业务表启用行级安全。**

对业务 schema 下的所有表执行两条设置：启用行级安全、强制行级安全。第二条很重要：如果不强制，表的所有者会自动绕过规则。

策略的内容是"只允许 `org_id` 等于当前事务上下文的行"。上下文由程序在事务开始时设置。如果程序忘记设置上下文，策略会不匹配任何数据，查询结果为空，而不是把全部数据暴露出来。

**第三步：把鉴权拆成两步。**

第一步用认证角色的连接验证会话和账号；第二步切换到业务角色的连接，并在事务里设置当前组织和当前用户。注意：**组织标识必须来自服务端的会话记录，绝对不允许客户端在请求里自己指定。** 这是防止越权的关键。

**第四步：实现集中式的权限控制。**

把"哪些角色能做什么"写成一个集中的控制模块，例如"只有管理员能管理成员""编写者不能归档项目"。路由里只调用这个模块，不要到处散落条件判断。这样做的好处是：权限规则只有一处，不容易出现遗漏。

**第五步：写负面测试。**

正常路径能跑通不代表安全。安全要靠"攻击自己"来验证。至少要写下面这些测试：

- 用甲组织的身份去读乙组织的项目，返回 404（注意：不是 403。因为 403 等于告诉对方"这个资源存在，但你没权限"，这本身也泄露了信息）。
- 用甲组织的身份去修改乙组织的资源，同样返回 404。
- 忘记设置租户上下文时，查询结果为空。
- 用业务角色尝试读取密码表，被数据库直接拒绝。
- 普通编写者尝试管理成员，被拒绝。

**第六步：写一个"串租户"回归测试。**

模拟连接池被反复借用的情况：先用甲组织的上下文执行一次查询，归还连接，再用没有上下文的连接执行一次查询，结果必须为空。这个测试用来证明上下文不会残留在连接里。

#### 怎么算做完了

- [ ] 上面五条负面测试全部通过。
- [ ] 故意把行级安全策略注释掉，负面测试会失败——这证明你的测试真的在起作用，而不是碰巧通过。
- [ ] 用数据库查询确认，业务角色没有超级权限，也不是表的所有者。
- [ ] 你能向别人解释清楚"应用层过滤"和"数据库层强制"为什么要同时存在。

#### 常见问题和提醒

**最常见的错误是：策略写了，但程序用的是表所有者的连接。** 表所有者默认可以绕过行级安全，所以策略形同虚设。解决办法是强制启用，并且用独立的低权限角色连接。

**第二个错误是把租户上下文设置成连接级别。** 必须使用事务级别的设置，事务结束就失效。否则连接被放回池子里，下一个请求会继承上一个请求的组织身份。

**第三个错误是跨组织返回 403。** 对不存在和无权限统一返回 404，可以避免攻击者通过状态码探测资源是否存在。

#### 这一步和企业开发的关系

多租户隔离是 SaaS 产品的核心安全设计。在企业里，这一块会有专门的安全评审和渗透测试。你在这个步骤里建立的"双重防护加负面测试"的思路，可以迁移到任何面向企业的系统。

### A6 项目模块与统一接口规范

**难度**：二星　**预计时间**：12 到 16 小时

#### 这一步要解决什么问题

前面几步处理的是"身份"和"安全"，从这个步骤开始写第一个真正的业务模块：项目。同时，这一步要把整个项目的接口"公共规矩"定下来，例如所有接口的返回格式、错误格式、分页方式、并发冲突处理、重复请求处理。后面所有模块都会直接复用这套规矩。

#### 动手之前，先弄懂几个词

**响应外壳**：所有成功返回都包成统一的结构，例如数据放在 `data` 字段里，另外带一个请求编号。这样前端可以用同一套代码处理所有接口的返回值。

**错误码**：每个业务错误有一个稳定的英文标识，例如版本冲突、项目已归档、任务还在运行。前端根据错误码决定怎么提示用户，而不是去猜提示文字。

**游标分页**：翻页的一种方式。它不记录"第几页"，而是记录"上一页最后一条的位置"，下一页从那个位置往后取。好处是数据不断增加时，翻页结果依然稳定，不会重复或者漏掉记录。

**乐观锁**：处理并发修改的一种方式。每条重要记录带一个版本号，用户提交修改时必须带上自己看到的版本号。如果数据库里的版本号已经变了，说明有人先改了，这次修改就被拒绝，提示用户刷新后重试。它的名字叫"乐观"，是因为它假设冲突不常发生，只在提交时检查。

**幂等**：同一个请求执行多次，效果和执行一次一样。例如用户点击"创建任务"时网络超时，他再点一次，系统不应该创建两个任务。

#### 具体怎么做

**第一步：实现统一响应和错误处理。**

按照 [API文档.md](./API文档.md) 第 1.2 节实现成功和失败的返回结构。写一个全局异常处理器，把程序里抛出的业务异常转换成对应的错误码、提示信息和可重试标记。请求编号要在每次请求开始时生成，并写进日志，方便排查问题。

**第二步：实现游标分页工具。**

写一个公共函数，接收页码大小和游标，返回数据列表和下一页游标。默认每页二十条，最多一百条。写测试证明：造二十五条数据，翻两页能全部取到，没有重复也没有遗漏。

**第三步：写项目相关的数据库迁移。**

创建项目表和章节目录表。项目表包含名称、工程类型、状态、当前基准标识、是否需要重新发布基准、版本号等字段。章节表在这一步只建目录所需的部分（标题、父节点、顺序），完整的版本和编辑器在 C4 步骤再做。这样安排是为了避免一次性引入太多概念。

**第四步：实现项目接口。**

实现查询列表、创建、查看详情、修改、归档五个接口。创建项目时要自动建立五个默认目录节点。修改和归档都必须带版本号，版本不一致返回冲突错误。

归档时有一个额外的检查：如果项目还有没结束的后台任务，拒绝归档并说明原因。这个检查依赖 A8 才完成的运行表，所以本步骤先留一个明确的待办标记，等 A8 完成后回填，并在 PR 描述里写清楚。

**第五步：实现幂等处理。**

创建一张幂等记录表（结构见 [数据库文档.md](./数据库文档.md) 第 12.2 节）。当一个请求带着幂等键进来时，系统先查这张表：如果同样的键和同样的请求体已经处理过，就直接返回上次的响应；如果键相同但请求体不同，返回冲突；如果上一个请求还在处理中，告诉客户端稍后再试。

**第六步：补测试。**

- 响应结构符合约定，每次请求的编号不同。
- 分页翻页不重不漏。
- 两个请求带同一个版本号修改同一条记录，只有一个成功。
- 同一个幂等请求重复提交，返回同一结果，不产生第二条数据。
- 归档带未完成任务的测试先标记为跳过，A8 之后启用。

#### 怎么算做完了

- [ ] 接口的字段和 [API文档.md](./API文档.md) 第 5 节逐项对照，没有偏差。
- [ ] 所有修改类接口都检查了版本号，没有"裸更新"。
- [ ] 幂等键的三种情况（重复、冲突、处理中）都有测试。
- [ ] 接口或数据库的偏差已经回写到对应文档。

#### 常见问题和提醒

**不要给每个接口各写一套错误格式。** 那样前端要做大量特殊处理，而且很容易出现不一致。统一格式一次做好，后面省事。

**不要用"先查询再更新"的方式实现并发控制。** 两个人同时查询到同一个版本号，然后都去更新，后提交的会覆盖先提交的。正确做法是把版本号写进更新条件里，让数据库来保证只有一个能成功。

**幂等记录不要只存在内存里。** 程序重启后内存就清空了，用户重试时可能产生第二个任务。

#### 这一步和企业开发的关系

企业里把这类工作叫"公共能力建设"或者"框架沉淀"。接口规范、分页、错误码、幂等、并发控制这些东西，越早统一越便宜。很多团队会专门维护一个公共库，就是这个原因。

### A7 前端最小闭环：登录页与项目列表

**难度**：二星　**预计时间**：16 到 24 小时

#### 这一步要解决什么问题

到目前为止，所有的功能都只能用命令行或者接口工具来验证。这一步要做出真正的浏览器界面，让你第一次有"这是一个产品"的感觉：打开页面、输入账号密码、看到项目列表、新建一个项目、把它归档。

同时，这一步要处理前端最容易被忽略的部分：加载状态、空列表、请求失败、登录过期。这些"不顺利的情况"才是用户最常遇到的。

#### 动手之前，先弄懂几个词

**前端**：运行在浏览器里的那部分程序。它负责显示界面、接收用户操作、调用后端接口。

**组件（Component）**：前端界面的一块可复用单元，例如登录表单、项目表格、确认弹窗。页面由组件拼装而成。

**路由（Routing）**：前端根据网址决定显示哪个页面。例如访问 `/login` 显示登录页，访问 `/projects` 显示项目列表。

**状态（State）**：前端需要记住的数据，例如"当前登录的用户是谁""项目列表是什么""弹窗是否打开"。

**开发代理**：开发阶段，前端运行在一个端口，后端运行在另一个端口。浏览器出于安全考虑不允许随便跨端口请求，所以通过代理把前端的接口请求转发给后端，让它们看起来像同一个来源。

**构建（Build）**：把开发时写的代码打包成浏览器可以直接加载的静态文件。部署时使用的就是构建产物。

#### 具体怎么做

**第一步：创建前端工程。**

```powershell
npm create vite@latest frontend -- --template react-ts
cd frontend
npm i antd react-router-dom @tanstack/react-query
```

第一条命令用 Vite 创建 React 加 TypeScript 的工程模板；第二条命令安装界面组件库、路由库和数据请求库。

**第二步：配置开发代理和代码规范。**

在 `vite.config.ts` 里配置：所有以 `/api` 开头的请求都转发到本机后端地址。然后配置 ESLint 和 Prettier，保证代码风格统一。最后确认 `npm run build` 能成功产出静态文件。

**第三步：封装统一的接口客户端。**

在 `src/api/` 目录里写一层封装，负责三件事：自动处理错误格式，把后端返回的错误码转换成界面提示；遇到"会话过期"时自动跳转到登录页；写操作自动带上 CSRF 令牌。

这里要再次强调：**会话凭证保存在 HttpOnly Cookie 里，前端代码不要接触它，也不要把任何身份信息写进 localStorage。**

**第四步：写登录页。**

页面包含三个输入框（组织标识、邮箱、密码）和一个登录按钮。提交后调用登录接口，成功就跳转到项目列表，失败就在页面上显示清楚的原因。注意按钮在请求期间要变成"提交中"状态，防止用户连点多次。

**第五步：写项目列表页。**

页面包含一个表格，显示项目的名称、工程类型、状态和更新时间；一个"新建项目"按钮，点击后弹出表单；每行有一个"归档"按钮，点击后弹出确认框，说明归档的后果。分页使用后端提供的游标。

**第六步：认真处理三种"不顺利"的状态。**

- **加载中**：显示加载动画或者骨架屏，不要白屏。
- **空列表**：显示一句引导性的话，例如"还没有项目，点击右上角新建一个"。
- **请求失败**：显示错误信息和一个重试按钮，不要把技术报错直接丢给用户。

另外，当后端返回"版本冲突"时，界面要提示"数据已经被其他人修改，请刷新后重试"，而不是简单报错。

**第七步（增强项）：加一条端到端冒烟测试。**

使用 Playwright 写一条最关键的测试：打开登录页、输入演示账号、登录成功、新建一个项目、确认列表里能看到它。这条测试以后会加入 CI，用来防止前端整体崩坏。

#### 怎么算做完了

- [ ] 浏览器里能完整走通：登录、查看列表、新建项目、刷新页面后数据还在、归档项目。
- [ ] 密码错误、会话过期、后端报错三种情况都有明确的界面提示。
- [ ] `npm run lint` 和 `npm run build` 没有错误。
- [ ] 断网之后刷新页面，界面给出提示，而不是白屏。
- [ ] 你能说清楚"为什么身份凭证不放 localStorage"。

#### 常见问题和提醒

**前后端字段命名不一致**是最常见的联调问题。后端习惯用下划线命名，前端习惯用驼峰命名，两边的转换要有统一的地方处理，不要在每个组件里各写一遍。

**登录过期不要只弹提示。** 正确的做法是清除本地状态并跳转到登录页，同时保留用户原本想去的地址，登录成功后跳回去。

**搜索框不要每敲一个字就发一次请求。** 要么等用户按回车再搜索，要么加一个短暂的延迟（防抖）。

#### 这一步和企业开发的关系

企业里前端通常先和后端约定接口文档，然后并行开发：前端用模拟数据先把页面搭好，后端把接口写好之后直接对接。你一个人做的时候顺序可以简化，但"先定接口、再做界面"的习惯要保持，因为接口就是前后端的合同。

### A8 后台任务与运行事件

**难度**：三星　**预计时间**：20 到 28 小时

#### 这一步要解决什么问题

解析文件、生成内容、导出文档这些工作很慢，可能几十秒到几分钟。如果让用户点击按钮之后一直等，页面会卡住，网络一断就前功尽弃。所以我们要把所有耗时工作交给"后台任务系统"来做，前端只负责显示进度。

这一步是整个阶段一最重要、也是最难的一步。完成后，你会拥有一个可靠的执行骨架：任务被创建、被排队、被领取、被执行、被记录，过程中产生的每一步进展都能实时推送到浏览器。

而且，这个骨架必须能应对各种意外：任务被重复投递、执行到一半进程崩溃、消息队列重启。这些在演示时看不出来，但决定了你的系统是"玩具"还是"能用"。

#### 动手之前，先弄懂几个词

**异步任务**：不在请求里当场完成、而是交给后台慢慢做的工作。

**Broker（消息中间件）**：存放待执行任务的地方。本项目使用 Redis 来担任这个角色。

**Worker（工作进程）**：从 Broker 里取出任务并执行的后台程序。

**Outbox（待投递表）**：数据库里的一张表，用来记录"有哪些任务需要投递出去"。为什么要它？因为"把数据写进数据库"和"把消息发进队列"这两件事没法保证同时成功。先在同一笔事务里写业务数据和待投递记录，再由一个独立的投递程序去发送消息，就能保证数据提交成功之后，任务最终一定会被投递。

**状态机**：描述"一个任务可以有哪些状态、状态之间怎么转换"的规则。例如任务不能从"已完成"变回"执行中"。

**租约（Lease）**：Worker 领取任务时获得的一个有时限的执行凭证。Worker 必须定期续约（发送心跳），如果租约过期，系统就认为这个 Worker 出了问题，可以把任务交给别人重做。

**Fencing Token（代际号）**：每次任务被重新领取，代际号就加一。Worker 提交结果时必须带上自己领取时的代际号，如果代际号已经不是最新的，说明它是一台"过期的 Worker"，结果会被拒绝。这样可以防止慢吞吞的 Worker 覆盖新 Worker 的结果。

**至少一次投递**：消息系统只能保证"消息至少被投递一次"，不能保证"恰好一次"。所以任务可能会被执行两次。我们通过幂等来保证重复执行不会产生重复结果。

**SSE（服务器推送事件）**：一种让服务器主动向浏览器推送消息的技术。本项目用它实时显示任务进度。

#### 具体怎么做

**第一步：写运行相关的数据库迁移。**

创建四张表：运行表（记录每次任务的总体状态和预算）、步骤表（记录任务内部的每个逻辑步骤）、事件表（记录推送给前端的事件）、待投递表。字段对照 [数据库文档.md](./数据库文档.md) 第 9 节和第 12.1 节。

**第二步：写状态机。**

先写纯函数，不碰数据库。定义允许的状态转换，例如"排队中"可以变成"执行中"，"执行中"可以变成"成功""失败""取消"；不允许的转换要明确拒绝。为每条合法转换和至少三条非法转换写单元测试。

**第三步：实现"创建运行"服务。**

在同一笔数据库事务里完成四件事：插入运行记录、插入第一条事件、插入待投递记录、记录幂等响应。这四件事必须要么全部成功，要么全部失败，不能出现"任务不存在但消息已经发出"的情况。

**第四步：实现投递程序。**

写一个独立的小程序，循环做这件事：从待投递表里领出一批记录，在事务外把消息发给消息队列，成功之后记录投递时间。消息内容只包含运行编号、组织编号和投递世代，不包含任何原文内容。

**第五步：实现 Worker。**

Worker 领取任务时要按固定顺序加锁（先锁项目，再锁运行），避免死锁。领取成功后设置执行者标识、代际号、租约过期时间，然后开始执行。

本步骤先用一个"假任务"来验证骨架：假装在处理文件，比如输出几条日志、等待三十秒、然后成功结束。为什么先用假任务？因为这样可以把"任务系统本身"的问题和"文档解析"的问题分开。等 B2 步骤接入真正的解析时，你会感谢现在的自己。

执行期间每二十秒续约一次心跳。每个节点提交结果之前都要检查：我还是当前的执行者吗？我的代际号还有效吗？租约还在吗？

**第六步：实现恢复巡检。**

写一个定时任务，每三十秒检查三类情况：租约已经过期的运行、排队很久没人领取的运行、到了重试时间的运行。符合条件的重新排队，重新领取时代际号加一。系统自动恢复的次数默认最多三次，超过之后标记为失败并说明原因，由用户手动决定是否重试。

**第七步：实现查询和控制接口。**

实现运行列表、运行详情、取消、恢复、重试五个接口。取消的语义要准确：排队中的任务可以立即取消；正在执行的任务只能登记"取消请求"，等 Worker 到达一个安全的检查点之后才算真正取消。界面上不能把"已请求取消"显示成"已取消"。

**第八步：实现事件推送接口。**

实现 SSE 推送。要点有四个：每十五秒发送一次心跳，防止连接被中间设备断开；事件编号的格式是"运行编号加序号"；支持浏览器断线重连后从上次的位置继续；任务到达终态之后关闭连接。

**第九步：写可靠性测试。**

这是本步骤最重要的部分，测试清单如下：

- 同一条待投递记录被重复投递，只产生一份业务结果。
- 执行过程中强行结束 Worker 进程，租约过期之后任务能自动恢复并最终成功。
- 重启 Redis 之后，还没被领取的任务仍然能被投递。
- 执行期间请求取消，任务在安全边界停止，不产生业务结果。
- 过期代际的 Worker 尝试提交结果，被拒绝。
- SSE 断线重连之后，事件不重复也不丢失。

#### 怎么算做完了

- [ ] 用一个测试脚本或临时接口创建假任务，能在浏览器或者命令行看到它从排队到成功的完整过程。
- [ ] 上面六条可靠性测试全部通过，并且加入 CI。
- [ ] 你能画出一张时序图，说明一次任务从创建到完成经过了哪些环节。
- [ ] 运行状态、步骤、事件在数据库里都能查到，不会出现"状态变了但没有对应事件"的情况。

#### 常见问题和提醒

**不要在请求线程里直接调用"发送任务"。** 如果数据库事务后来回滚了，任务却已经发出去了，就会产生一个"幽灵任务"。

**不要把 Redis 当成状态存储。** Redis 可能重启，重启后内存里的数据就没有了。业务状态必须存在 PostgreSQL 里，Redis 只是消息的搬运工。

**不要在 Worker 里用长事务包住模型调用。** 模型调用可能要一两分钟，长事务会占着数据库连接不放，连接池很快就被耗光。

#### 这一步和企业开发的关系

异步任务、可靠投递、租约与幂等，是 AI 应用后端岗位面试的高频考点。很多个人项目能演示"点击之后生成内容"，但经不起"任务重复了会怎样""进程崩了会怎样"的追问。你把这个步骤做扎实，就已经超过大部分同类作品。

### B1 文件上传与对象存储

**难度**：二星　**预计时间**：14 到 20 小时

#### 这一步要解决什么问题

用户要把招标文件、企业资料这些文件交给系统。这一步要解决四个问题：文件怎么安全地上传、存到哪里、怎么记录它的状态、怎么保证只有有权限的人才能下载。

还有一个容易被忽略的要求：原始文件永远不能变。同一份文件如果上传了新版本，旧版本要保留，因为之前发布的基准里可能还引用着旧版本。

#### 动手之前，先弄懂几个词

**对象存储**：专门用来存文件的系统。它不关心文件内容，只负责把文件安全地存起来、取出来。它比直接存进数据库更合适，因为数据库更适合存结构化数据，放大文件会拖慢备份和查询。

**S3 协议**：对象存储的一种通用接口标准。很多产品都兼容它，所以我们的代码只针对这个标准编写，将来换供应商时不用改业务代码。

**流式读取**：一边从网络接收文件，一边处理，而不是等整个文件到齐再处理。大文件必须用流式方式，否则内存会被撑爆。

**SHA-256**：一种文件指纹算法。两个文件只要内容有一点不同，指纹就完全不同。我们用它来校验文件有没有损坏或被替换。

**孤儿对象**：已经存进对象存储、但数据库里没有对应记录的文件。它们通常是"存文件成功、登记数据库失败"造成的，需要定期清理。

**Range 请求**：只请求文件的一部分，例如"只要第 100 到 200 字节"。PDF 阅读器靠它实现快速加载和跳页。

#### 具体怎么做

**第一步：写文档相关的数据库迁移。**

创建逻辑文件表、文件版本表、解析块表。逻辑文件代表"这一份资料"，文件版本代表"这份资料的第几次上传"。解析块表本步骤先建好，B2 步骤再使用。字段对照 [数据库文档.md](./数据库文档.md) 第 6.2 到 6.4 节。

注意三套状态是分开的：解析状态（有没有解析成功）、确认状态（用户有没有确认可用）、索引状态（有没有建好检索索引）。它们各自独立变化，不能用一个字段表示。

**第二步：封装存储适配器。**

写一个存储模块，对外只暴露四个操作：保存、读取、删除、判断是否存在。业务代码只调用这四个操作，不直接使用对象存储的软件开发包。这样做的好处是：将来更换存储服务时，只需要改这一个文件。

**第三步：实现上传接口。**

上传的处理顺序是：流式读取文件并检查大小；检查扩展名和文件真实类型是否一致；计算 SHA-256；先保存到临时的私有位置；确认保存成功之后，再在一笔数据库事务里登记文件、文件版本和解析任务。如果数据库登记失败，临时对象留给清理程序回收，不影响用户。

**第四步：做文件安全检查。**

至少要做三件事：读取文件头，判断它是不是真的 PDF 或 DOCX，防止把可执行文件改名上传；对 DOCX 做解压炸弹防护，检查压缩包里的文件数量和展开后的大小；文件名只用来显示，绝不能用来拼接服务器路径，否则会有路径穿越漏洞。

**第五步：实现受权下载。**

下载接口要先检查登录和所属组织，再返回文件。支持 Range 请求，正常返回 206，区间非法返回 416。PDF 允许在浏览器里直接预览，DOCX 默认作为附件下载。返回信息里不能出现存储内部路径或者长期有效的公开链接。

**第六步：实现资料确认接口。**

用户确认资料时，要记录：确认状态、是否允许把内容发送给云端处理、许可说明。有一个重要规则：**撤销外发许可要立刻生效**。如果这个资料被某个项目基准引用，撤销许可要让项目进入"需要重新发布基准"的状态。

**第七步：写孤儿清理脚本。**

脚本先输出"哪些对象没有数据库引用、最后修改时间超过二十四小时"，让你人工确认，然后才真正删除。永远先做试运行，再做真删除。

**第八步：补测试。**

- 超过大小限制返回 413。
- 格式不支持或者伪装扩展名返回 415。
- 跨组织下载返回 404。
- Range 请求正确返回 206，非法区间返回 416。
- 故意让数据库登记失败，确认对象能被清理脚本识别。
- 解析还没完成就确认资料，返回"资料尚未就绪"。

#### 怎么算做完了

- [ ] 上面六条测试全部通过。
- [ ] 存储适配器可以替换，业务代码里没有出现存储服务的专属调用。
- [ ] 数据库里的状态字段与 [数据库文档.md](./数据库文档.md) 第 6.3 节逐项对照。
- [ ] 你能解释为什么三套状态要分开。

#### 常见问题和提醒

**不要把大文件直接存进数据库。** 数据库适合存结构化数据，文件放进去会让备份变得又慢又大。

**不要相信用户提供的文件名。** 文件名里可能藏着 `../` 这样的路径片段，直接使用会造成安全问题。

**上传成功不等于资料可用。** 解析是后台任务，界面要显示"已上传、处理中"，解析完成确认之后才显示"可用"。

#### 这一步和企业开发的关系

对象存储、上传安全、数据生命周期管理，是"文件类产品"的第一道工程题。企业里还会加上病毒扫描、水印、访问审计、存储加密等要求，但基本结构和你在这一步做的是同一套。

### B2 文档解析与来源定位

**难度**：三星　**预计时间**：20 到 28 小时

#### 这一步要解决什么问题

计算机看不懂 PDF 的排版，也看不懂 Word 的样式。这一步要把文件变成结构化的内容块：每个块知道自己是标题还是段落还是表格，知道自己属于哪个章节，知道自己在原文里的准确位置。

这是整个项目证据链的地基。后面所有"这句话来自哪里"的能力，都依赖这一步的准确性。所以这个步骤值得慢慢做、仔细测。

#### 动手之前，先弄懂几个词

**解析**：把文件内容转换成程序可以处理的结构化数据的过程。

**块（Block）**：解析结果的最小单元，可以是一个标题、一个段落或者一张表格。

**标题路径**：这个块所属的章节层级，例如"评标办法 → 技术评分 → 施工方案"。

**来源定位**：这个块在原文里的位置。PDF 用"第几页加一个矩形区域"表示；Word 用"标题路径加上第几段或者第几行第几列"表示。

**归一化坐标**：把坐标换算成 0 到 1 之间的小数，而不是绝对像素。这样无论页面显示多大，位置都能对得上。

**扫描件**：整页是图片、没有文字层的 PDF。这种文件需要光学字符识别才能处理，而第一版明确不支持，遇到时返回清晰的提示，而不是假装解析成功。

#### 具体怎么做

**第一步：在解析任务里接入文档解析库。**

Worker 从对象存储下载文件到受控的临时目录，调用解析库转换成统一结构，然后把结果整理成本项目的块结构。临时目录要及时清理，并且要限制解析的超时时间和资源占用。

**第二步：生成解析块。**

每个块要记录：顺序编号、类型、标题路径、纯文本内容、表格数据（如果是表格）、来源定位、内容哈希。字段对照 [数据库文档.md](./数据库文档.md) 第 6.4 节。

PDF 的定位用页码加矩形区域；Word 的定位用标题路径加段落序号，或者是表格的行列位置。特别注意：**Word 不提供页码**，因为 Word 的分页是渲染时动态计算的，同一份文件在不同电脑上分页可能不同。硬造页码是不诚实的。

**第三步：做解析质量检查。**

解析结束之前要检查：提取到的文字量是否合理、页数是否超过上限、每个块的定位是否有效。如果是扫描件、空文档或者损坏文件，要返回明确的错误原因，例如"这是扫描件，第一版不支持""文件已损坏""文件超过页数限制"。

**第四步：限制资源占用。**

给解析任务设置超时时间、内存上限，并且把每个任务放在独立的临时目录里。解析库需要的模型文件要在构建镜像或者初始化阶段提前下载好，并记录校验和，避免演示现场卡在"正在下载模型"上。

**第五步：一次性提交结果。**

所有解析块、解析状态、解析器版本号、完成事件必须在同一笔事务里提交。失败的话只更新状态和错误原因，不留下半截数据。这样就不会出现"读到了半份解析结果"的情况。

**第六步：实现块查询接口。**

提供按文件版本查询块列表、按块编号查询单个块的接口。返回内容包括定位信息和文件访问路径，但不包含存储系统的内部信息。

**第七步：处理重试。**

只有解析失败或者不支持的版本可以重新解析。已经解析成功的文件不能原地重新解析，需要重新解析就上传一个新版本。这样保证历史记录里的定位始终指向当时的内容。

**第八步：准备样本并测试。**

- 一份正常 PDF：检查块数量、页码、区域是否合理。
- 一份正常 DOCX：检查标题路径和表格定位是否正确。
- 一份扫描 PDF：返回"不支持扫描件"。
- 一份损坏文件：返回"文件损坏"。
- 一份超过页数限制的文件：返回"超出限制"。
- 随机抽取十个块，用它们的定位信息去原文里核对位置是否准确。

#### 怎么算做完了

- [ ] 五类样本的结果都符合预期，测试进入 CI（大文件可以标记为慢测试，单独运行）。
- [ ] 随机抽检的块定位准确。
- [ ] 你能解释为什么解析块和定位信息不可修改。
- [ ] 项目里有一份说明：支持什么格式、不支持什么、失败时会怎样。

#### 常见问题和提醒

**不要给 Word 文件编造页码。** 这是本步骤最容易犯的错。Word 的页码取决于渲染环境，编一个页码看起来专业，实际会误导用户。

**重试解析时不要留下重复的块。** 先清理旧结果再写入新结果，而且要在同一笔事务里完成。

**不要把 PDF 的绝对坐标直接存进数据库。** 要归一化，否则缩放之后高亮区域就会错位。

#### 这一步和企业开发的关系

在企业里，这一步属于"文档数据处理"或者"数据管道"。真实项目会在这里投入大量测试样本和人工抽检，因为大家都很清楚一句话：垃圾进，垃圾出。你的解析质量，直接决定后面所有功能的上限。

### B3 招标分析与项目基准

**难度**：三星　**预计时间**：18 到 26 小时

#### 这一步要解决什么问题

招标文件是一份几百页的文档，里面真正需要响应和评分的内容可能只有几十条。这一步要做的，是把这些内容抽取出来，交给人工确认，然后把确认结果冻结成一份不可修改的"基准"。

基准是这个项目最重要的业务概念。你可以把它理解成：**在某个时间点，给这个项目的全部确认结果拍一张照片，之后所有生成、审查、审核、导出都以这张照片为准。** 这样无论后面资料怎么更新、要求怎么修改，已经完成的审核和导出都有据可查。

#### 动手之前，先弄懂几个词

**要求（Requirement）**：招标文件里需要投标方响应的内容，分三类：强制性要求、评分项、一般要求。

**事实（Fact）**：项目或者企业的确定信息，例如工期一百八十天、项目负责人是谁。事实分两类：来自招标文件的招标事实，来自企业资料的企业事实。

**草稿与确认**：抽取出来的内容一开始都是草稿，必须人工检查确认之后才能进入基准。这样设计是为了防止模型的错误直接变成正式依据。

**快照**：某一时刻数据的完整副本。注意，快照要保存实际内容，而不是只保存编号。如果只保存编号，将来原记录被修改，历史快照就被间接改掉了。

**哈希**：给快照算一个指纹。同样的内容算出来的指纹一定相同，内容有任何变化指纹就不同。它用来判断两份基准是不是同一个内容。

**脏标记（Dirty Flag）**：一个开关，表示"确认数据已经发生变化，但还没有重新发布基准"。处于脏状态时，系统禁止生成、审核和导出，避免有人用旧基准做新事情。

#### 具体怎么做

**第一步：写分析和基准相关的数据库迁移。**

创建要求表、事实表、基准表、章节要求映射表。字段对照 [数据库文档.md](./数据库文档.md) 第 7 节。特别要注意来源字段的约束：来自文件的要求必须有来源块编号，人工录入的必须有来源说明。

**第二步：实现分析任务。**

分析任务只接受"本项目招标类型、已解析、已确认"的文件版本，一次可以分析一到十份。云端模式还要求这些文件允许外发处理，否则直接拒绝。模拟模式可以用于测试。

这里有一个重要的做题顺序：**先用确定性规则把整条流程跑通。** 例如用规则识别"工期""质量目标""评分"这些关键词和数字。为什么先用规则？因为规则的结果是确定的、可重复的，能帮你验证"抽取、落库、去重、确认、发布"这条流水线是否正确。等到 C1 步骤模型网关做好了，再把规则抽取替换成模型抽取，两者共用同一套后续逻辑。

**第三步：处理未知值。**

原文没有明确写出的信息，一律留空，绝对不要猜。例如原文只写了"工期见合同"，那就不能填一个默认数字。这一条要写进测试：构造一个缺少工期数字的样本，断言抽取结果里工期为空。

**第四步：实现人工修订与确认。**

要求、事实的修改都要带版本号。确认和拒绝要记录确认人和确认时间。人工新增内容必须写来源说明。修改任何确认数据之后，项目的"脏标记"要被设置，同时在界面上提示"需要重新发布基准"。

**第五步：守住三类事实的边界。**

招标事实只能来自本项目的招标文件；企业事实只能来自企业资料；历史标书不能用来证明企业能力。这条规则要写成测试，因为它是防止"AI 编造公司业绩"的关键一道闸门。

**第六步：实现基准发布。**

发布基准要在一把项目级的锁里完成，依次做：检查至少有一条已确认的要求；检查所有来源文件都已解析、已确认、未被归档；把要求、事实、资料版本和章节映射的实际内容复制进快照；计算快照哈希；创建基准记录；更新项目的当前基准指针；把脏标记清除；把所有章节标记为需要复核。

注意最后一条：每次发布新基准，所有章节都要重新复核。因为基准变了，之前基于旧基准做的工作都需要重新检查。

**第七步：处理"相同内容重复发布"。**

如果用户连续发布两次，而内容完全一样，系统应该返回已有的基准，而不是每次都新建一个版本。判断的依据就是快照哈希。

**第八步：补测试。**

- 没有已确认要求时发布失败。
- 来源文件没确认或者被归档时发布失败。
- 两次相同内容发布只产生一个版本。
- 发布之后修改一条要求，脏标记变成真，旧快照内容不变。
- 尝试修改已经发布的快照，接口不存在，数据库层面也拒绝。

#### 怎么算做完了

- [ ] 能演示完整流程：分析、人工修订、确认、发布基准、查看快照。
- [ ] 快照哈希在两次独立运行中完全一致。
- [ ] 你能画图说明"草稿数据"和"快照数据"的关系。
- [ ] 你能解释为什么快照不能只存编号。

#### 常见问题和提醒

**最常见的错误是把快照存成编号列表。** 这样一旦原始记录被修改，历史快照就被污染了，审计也就失去意义。

**第二个错误是发布基准不加锁。** 两个人同时发布，可能产生两个"当前基准"，后面所有依赖"当前基准"的逻辑都会出问题。

**第三个错误是脏标记只在部分入口设置。** 只要有一个修改入口忘记设置，用户就会用旧基准做出错误的新内容。解决办法是写测试穷举所有修改入口。

#### 这一步和企业开发的关系

基准管理、快照和审计，是金融、医疗、工程这些行业的核心合规手段。面试时如果能讲清楚"为什么要做快照而不是实时读取"，会非常加分，因为它体现的是对业务风险的理解，而不只是会写代码。

### B4 检索与索引

**难度**：三星　**预计时间**：24 到 32 小时

#### 这一步要解决什么问题

用户提问或者系统生成内容时，需要从资料里找到相关证据。最简单的做法是全文搜索关键词，但这样做有两个问题：一是中文分词不准，二是同义表达搜不到。所以我们要做两套检索，再把结果融合起来。

同时，检索必须遵守权限和状态：不能搜到别的组织的资料，不能搜到没有确认的资料，不能搜到已经归档的资料。

#### 动手之前，先弄懂几个词

**索引**：为了加快搜索速度而额外建立的数据结构。就像书后面的索引，不需要把整本书读一遍就能找到内容。

**分词**：把一句话切成一个个词。中文没有空格，所以需要专门的分词工具。例如"施工组织设计"要切成"施工""组织""设计"。

**受保护词**：不应该被切开的词，例如标准编号、设备型号、项目编号。这些词一旦被切开，搜索就找不到了。

**词项检索**：基于词语的搜索方式。优点是准确、快速、结果可解释；缺点是无法处理同义表达。

**向量检索**：把文字转换成一组数字（叫向量），用数字之间的距离衡量语义相似度。优点是能理解"意思相近"；缺点是不够精确、需要模型支持。

**混合检索**：同时使用词项检索和向量检索，然后把两个结果列表合并。

**RRF（倒数排名融合）**：一种合并排名的方法。一个内容在词项检索里排第三、在向量检索里排第十，它会得到一个综合分数。这种方法只需要排名，不需要把两种分数换算到同一个尺度。

**索引配置（Profile）**：记录这次索引使用的分词版本、切块方式、向量模型和维度。不同的配置不能混用，否则结果没有可比性。

#### 具体怎么做

**第一步：写检索相关的数据库迁移。**

启用向量扩展，创建索引配置表、词项索引表、向量索引表。字段对照 [数据库文档.md](./数据库文档.md) 第 6.5 到 6.7 节。向量维度第一版固定为一千零二十四。

**第二步：实现中文分词。**

在程序里实现分词，把标题路径和正文拼在一起作为可搜索文本。标准编号、型号、项目编号要在分词前保护起来。分词器的版本号要写进索引配置，保证"入库时用的分词规则"和"查询时用的分词规则"完全一致。

**第三步：实现索引任务。**

复用 A8 的后台任务框架。词项索引只要资料已解析、已确认就能建立，不需要外发许可。向量索引只有在资料允许外发、并且云端模型的配置完整时才建立。只允许本地处理的资料，绝对不能产生云端向量。

索引任务要幂等：同样的文件版本加同样的索引配置，重复执行不产生重复数据。

**第四步：实现检索接口。**

检索请求要带查询文字、检索模式、是否允许把查询发给云端、资料范围等参数。服务端执行的过滤包括：组织、项目或共享范围、资料用途、确认状态、解析状态、是否归档、索引配置。任何一条不满足都不能出现在结果里。

**第五步：实现结果融合。**

词项检索取前三十条，向量检索取前三十条，用倒数排名融合算出综合排名，最后返回前二十条。生成内容时默认取前八条，并且要控制上下文长度，不能把整段资料全塞进去。

**第六步：实现降级语义。**

如果用户要求混合检索，但向量不可用，系统要如实返回"实际使用的是词项检索"以及原因，不能把词项结果伪装成混合结果。云端生成任务在缺少向量时也不能悄悄降级成模拟模式。

**第七步：第一版先用精确检索。**

数据量小的时候直接逐个计算相似度就够了，不需要建立近似索引。等到数据量增长、并且评测证明有必要时，再考虑添加近似索引。盲目添加复杂索引只会让调试变难。

**第八步：建立检索评测集。**

准备十到二十个问题，每个问题标注正确的证据块。写一个脚本自动计算"前十名里包含正确证据的比例"，输出到评测报告目录。样本少没关系，但要如实记录样本量和结论适用范围。

**第九步：补测试。**

- 搜索标准编号和型号能命中（受保护词生效）。
- 跨组织、未确认、已归档的资料不出现在结果里。
- 只允许本地处理的资料在混合模式下没有向量、也不会被外发。
- 向量维度不一致时明确报错，不静默截断。
- 相同输入重复检索，排序结果稳定。

#### 怎么算做完了

- [ ] 词项检索和模拟向量下的混合检索都能跑通。
- [ ] 接口字段与 [API文档.md](./API文档.md) 第 8 节一致。
- [ ] 第一版检索评测报告存在，记录了样本、指标和失败案例。
- [ ] 你能解释为什么更换向量模型必须建立新的索引配置。

#### 常见问题和提醒

**查询和入库使用不同的分词配置**，是检索效果差的最常见原因，而且很难排查。所以配置版本要落库、要可对比。

**不要把向量存成文本或者普通数组。** 必须使用数据库提供的向量类型，才能正确计算距离。

**检索不过滤确认状态**是严重的合规问题：未确认的资料进入生成上下文，等于让没有依据的内容进入正式成果。

#### 这一步和企业开发的关系

搜索和检索质量工程是 AI 应用里"看起来简单、做好很难"的典型模块。企业里会专门建立评测集，每次调整分词、切块、模型都跑一遍回归，防止效果悄悄变差。

### C1 模型网关与成本记账

**难度**：二星　**预计时间**：14 到 20 小时

#### 这一步要解决什么问题

从这一步开始，系统要调用 AI 模型了。但直接在业务代码里调用供应商接口会带来四个问题：换供应商要改很多地方、超时和限流处理到处重复、调用结构没人统一校验、花了多少钱说不清楚。所以我们要建一个"网关"，所有模型调用都必须经过它。

这一步还有一个教学上的目的：**先用模拟模式把整条链路跑通。** 模拟模式不调用云端，不需要密钥，不产生费用，输出是固定可重复的。这样你就能在没有网络、没有预算的情况下，验证整个业务流程是否正确。等业务流程稳定之后，再切换到真实模型。

#### 动手之前，先弄懂几个词

**网关（Gateway）**：系统的统一出入口。所有模型调用从这里经过，方便统一管理。

**适配器（Adapter）**：把不同供应商的接口转换成统一接口的代码。供应商的软件开发包只能出现在适配器里。

**模拟模式**：用假数据代替真实模型调用的运行模式。所有模拟结果在界面上都要明确标注，绝不允许把模拟结果说成真实模型效果。

**结构化输出**：要求模型按指定格式返回数据，例如固定的字段和类型，而不是一段自由文字。这样程序才能可靠地处理结果。

**Schema 校验**：检查模型返回的结构是否符合约定。不符合时可以给模型一次修复机会，再不符合就报错。

**预算预留与结算**：调用之前先按最大消耗预留额度，调用返回之后按实际用量结算。这样能防止并发调用把预算花超。如果调用超时、结果未知，预留额度不能释放，要标记为"未知用量"。

**外发清单**：记录这次调用把哪些资料片段发送出去了。它回答的问题是："哪些资料被发给了外部模型？"

#### 具体怎么做

**第一步：写模型调用记录的数据库迁移。**

创建模型调用表，字段对照 [数据库文档.md](./数据库文档.md) 第 9.4 节。重点字段包括：请求指纹、外发清单、调用状态（开始、成功、失败、未知）、预留和实际用量、费用、代际号。

**第二步：定义网关接口。**

网关对外只暴露两个能力：结构化生成和向量计算。返回值必须经过结构校验，校验失败算一次格式修复机会，最多修复一次。

**第三步：实现两个适配器。**

第一个是模拟适配器，输出确定性的假结果，用于开发和测试；第二个是真实供应商适配器，本项目的默认供应商是通义千问，密钥从环境变量读取。再次强调：供应商的软件开发包只能出现在适配器文件里。

**第四步：实现调用治理。**

连接超时十秒，生成响应超时一百二十秒。只对网络错误和限流错误重试，最多重试两次，重试间隔按指数增长并加入随机扰动。每次调用之前先写一条"已开始"的记录并预留预算，返回之后更新用量和费用。

超时或者进程退出可能留下"未知"状态的调用。处理原则是：**保留预留额度，标记为未知，绝不当作零费用。** 后续如果拿到供应商的账单或者回调，再更新这条记录。

**第五步：管理运行模式。**

配置里有两个模式：模拟和云端。页面和接口返回里要明确告诉用户当前使用的是哪个模式。云端模式需要的配置缺任何一项，启动检查就要失败或者明确禁用模型任务，不允许运行到一半才悄悄降级。

**第六步：建立提示词模板。**

提示词写在单独的目录里，每个模板分六个部分：任务说明、事实、要求、证据、输出格式、禁止行为。模板带版本号，版本号要记录进生成快照，方便回溯。

**第七步：把前面的抽取和向量调用切换成走网关。**

B3 步骤里的规则抽取升级成模型抽取，B4 步骤里的向量计算换成网关的向量接口。两条路径共用同一套落库、确认和索引逻辑，所以这次切换只需要改"来源"，不需要改下游。

**第八步：写合同测试。**

用假的供应商服务模拟这几种情况：返回结构不符合约定、返回限流错误、请求超时、返回里缺少用量信息、向量维度不对、预算不足。每一种情况都要验证系统给出正确的错误码和状态，而不是崩溃或者静默出错。

#### 怎么算做完了

- [ ] 模拟模式下，分析和检索全链路能跑通，界面明确标注模拟结果。
- [ ] 模型调用记录能回答：这次运行花了多少、用了什么模型、哪些资料被外发过。
- [ ] 断网时模拟模式一切正常；云端配置缺失时启动检查失败。
- [ ] 供应商软件开发包只出现在适配器文件里（用搜索命令确认）。
- [ ] 上面六种合同测试全部通过。

#### 常见问题和提醒

**不要把供应商的调用散落在各个业务模块里。** 那样将来换模型时，你会需要改十几个文件。

**超时之后不要直接重新发送。** 第一次调用可能已经成功并且已经计费，只是响应没回来。此时应该标记为未知并保留预算，由人工或者对账流程处理。

**预算不能只在事后统计。** 必须调用前预留，否则并发调用会把预算用超。

#### 这一步和企业开发的关系

AI 网关和成本治理是 AI 应用工程师的核心竞争力之一。企业里还会加上多供应商路由、缓存、限流配额、内容安全审核等能力，但基础结构就是你在这一步搭建的这套。

### C2 生成图：LangGraph 流水线

**难度**：三星　**预计时间**：20 到 28 小时

#### 这一步要解决什么问题

"生成一章内容"不是一个动作，而是一串动作：准备、检索、检查缺口、生成、规则检查、语义审查、修订、保存。如果把这些动作写成一个几百行的大函数，会非常难维护、难调试、难恢复。

这一步要把它们拆成一个个独立的节点，用工作流引擎串起来。每个节点只做一件事，做完记录结果；整条流程可以暂停、可以重放、可以在中断之后从断点继续。

本步骤先完成"没有缺口"的主路径。遇到缺口暂停的情况在 C3 步骤实现。

#### 动手之前，先弄懂几个词

**图（Graph）**：由节点和连线组成的工作流。节点是具体动作，连线决定执行顺序。

**节点（Node）**：工作流里的一个步骤，例如"检索证据"就是一个节点。

**状态（State）**：在节点之间传递的数据，例如当前章节、基准编号、检索到的证据、生成的草稿。

**检查点（Checkpoint）**：工作流状态的存档。进程崩溃之后，可以从最近一次存档继续执行。

**格式修复**：模型返回的结构不符合约定时，把错误信息告诉它，让它重新输出一次。

**修订轮数**：发现问题之后允许模型修改内容的次数。本项目最多两轮，超过就停止修订并保留问题。

**幂等产物**：同一个任务重复执行不会产生两份结果。做法是执行之前先查"这个运行是不是已经产出过结果"。

#### 具体怎么做

**第一步：搭出图的骨架。**

节点顺序固定为：准备、检索、缺口检查、生成、规则检查、语义审查、有限修订、保存候选。

**第二步：定义图的状态。**

状态里至少要有：运行编号、章节编号、基准编号、快照哈希、基底版本、提示词版本、模型配置、索引配置、冻结的要求和事实、可用资料版本、证据编号、缺口列表、草稿内容、结构化问题、修订次数、格式修复次数、预算使用情况、最终产物编号。

注意：**不要把大段原文放进状态里**，状态里只放编号和摘要，正文和完整资料放在业务表里。否则检查点会变得非常大。

**第三步：接入数据库检查点。**

用运行编号作为线程标识，把图的状态存进 PostgreSQL。每次访问检查点之前，先验证这个运行确实属于当前组织。

这里要理解一个设计：**业务成果以业务表为准，检查点只是恢复用的辅助。** 如果进程在"业务结果已提交、检查点还没更新"之间崩溃，恢复时要先检查业务结果是否已经存在，避免重复写入。

**第四步：逐个实现节点。**

- 准备节点：检查基准是当前的、没有脏标记、章节映射和许可有效，然后冻结上下文和预算。
- 检索节点：只在基准冻结的资料版本里检索，不能用后来上传的新版本。
- 生成节点：要求模型区分"确认的事实"和"建议的措施"，引用只能用系统给的证据编号，模型不能自己编页码。
- 规则检查节点：调用 C5 步骤的规则引擎，本步骤先留好接口。
- 语义审查节点：对照要求检查响应情况，先用简化版本，D1 步骤再完善。
- 有限修订节点：最多两轮，超限就停止并保留问题。
- 保存候选节点：先查有没有重复产物，再校验租约和取消状态，最后写入。

**第五步：记录步骤和事件。**

每个节点开始时写一条"步骤开始"，结束时写"步骤完成"或者"步骤失败"，同时更新预算使用情况。重放的时候先检查这个步骤是不是已经成功过。

**第六步：写模拟模式测试。**

- 正常路径能跑完，产出一个候选版本，而且章节当前采用的内容没有被改动。
- 把整条流程重放一遍，不会产生第二个候选版本。
- 准备阶段发现基准变脏，拒绝执行。
- 检索不到任何证据，进入缺口分支。
- 格式修复次数、修订轮数和预算统计符合预期。

#### 怎么算做完了

- [ ] 模拟模式下，"生成一章"从创建任务到候选版本可以完整演示。
- [ ] 图的状态字段与设计文档一致。
- [ ] 节点失败时，能清楚知道停在哪一步、失败原因是什么。
- [ ] 你能讲清楚 LangGraph 负责什么、数据库负责什么。

#### 常见问题和提醒

**把完整原文放进工作流状态**是最常见的错误，会让检查点迅速膨胀。

**节点直接输出自由文本**也不行。每个节点必须先产出结构化结果，再由渲染层把它变成正文。

**修订不能没有上限。** 必须有硬性计数，超过就停，否则可能无限循环，费用失控。

#### 这一步和企业开发的关系

工作流编排、状态机设计和可重放性，是"从调用模型的脚本"到"生产级 AI 应用"的分水岭。企业里会把这类能力沉淀成平台，让业务团队复用。

### C3 缺口暂停与断点恢复

**难度**：三星　**预计时间**：18 到 26 小时

#### 这一步要解决什么问题

生成内容时经常会遇到"资料不够"的情况，例如招标文件要求响应某项内容，但企业资料里没有对应证据。这时候系统不能硬编，而应该停下来，清楚地告诉用户缺什么，等用户处理之后继续。

暂停还有一个工程要求：暂停期间不能一直占用 Worker。Worker 是很宝贵的资源，全国各地的任务都在排队等它。所以暂停时要释放租约，恢复时重新排队。

#### 动手之前，先弄懂几个词

**人工中断**：工作流执行到某个节点时主动停下，等待外部输入，然后再继续。

**恢复决策**：用户对暂停的任务做出的选择。本项目有两种：保留待补项继续，或者取消。

**基准过期**：暂停期间项目的基准发生了变化。此时原任务不能恢复，因为它的输入已经过时了。

**安全边界**：Worker 在运行过程中会定期检查"有没有取消请求"。检查点所在的位置就叫安全边界。只有到达安全边界，取消才算真正完成。

**重试**：失败的任务重新执行。注意，本项目不允许在原任务上原地重试，而是创建一个新任务，并记录它重试自哪个任务。

#### 具体怎么做

**第一步：实现缺口暂停。**

缺口检查节点发现问题时，触发人工中断，把缺口整理成结构化列表，内容包括：缺什么、为什么必须有、建议怎么补。任务进入"等待输入"状态，并把等待内容记录到运行记录里。

**第二步：暂停时释放租约。**

任务进入等待状态之后，清空执行者信息和租约过期时间，让 Worker 可以去做别的任务。恢复时重新排队，代际号加一。

**第三步：实现恢复接口。**

恢复请求必须确认所有当前缺口，并且要带幂等键。恢复的决策只有两种：保留待补项继续，或者取消。**不允许通过恢复接口传入新的事实、新的文件或者新的模型配置**，这样是为了保证任务的输入不会被人悄悄改变。

恢复之前要检查基准：如果基准变脏，返回"需要重新发布基准"；如果基准已经不是当前版本，返回"基准已过期"。

**第四步：实现取消。**

排队中、等待输入、等待重试的任务可以立即取消。正在执行的任务只能登记取消请求，等 Worker 到达安全边界之后才算取消完成。接口返回当前的真实状态，界面上要区分"已请求取消"和"已取消"。

**第五步：实现失败重试。**

只有失败的任务能重试。重试会创建一个新任务，关联原任务，继承输入快照，并且重新检查当前基准和许可。原任务保持失败状态，不会被覆盖，方便事后分析。

**第六步：完善恢复巡检。**

系统自动恢复的次数有上限，默认三次。超过上限之后任务标记为失败，并写明"自动恢复次数已用尽"，由用户决定是否手动重试。

**第七步：写并发和恢复测试。**

- 暂停之后结束 Worker 进程，恢复之后任务仍能继续。
- 同一个项目同时发起第三条生成任务，它保持排队，不会获得执行权。
- 过期代际的 Worker 尝试提交结果，被拒绝。
- 重复提交同一个恢复请求，返回原结果，不会重复执行。
- 恢复时基准已经变化，返回"基准已过期"，任务仍然可以查看和取消。
- 取消之后任务不再产生任何业务结果。

#### 怎么算做完了

- [ ] 上面六条测试全部通过，并加入集成测试目录。
- [ ] 能演示：生成过程中故意缺少证据，任务暂停；处理之后恢复；最终完成。
- [ ] 运行详情里能看到阶段、暂停原因、事件和用量。

#### 常见问题和提醒

**暂停时如果没有释放租约**，Worker 会被一个等待人工的任务占住，后面的任务全部排队。

**恢复时如果不检查基准**，用户可能用一个过期的依据继续生成，产出无效内容。

**不要把"取消请求"直接显示成"已取消"**，这会误导用户以为资源已经释放、结果已经停止产生。

#### 这一步和企业开发的关系

长时间任务的可靠性设计是人机协作产品的核心。企业里会专门做故障注入测试：故意杀进程、故意断网、故意重启中间件，验证系统能不能自愈。你在这一步做的测试，就是这套演练的雏形。

### C4 章节编辑器与版本管理

**难度**：三星　**预计时间**：24 到 32 小时

#### 这一步要解决什么问题

前面生成出来的内容还只存在于后台数据里，用户看不见、改不了。这一步要做两件事：给用户一个可以编辑章节的界面；建立一套严格的版本规则，让每一次修改都有记录，AI 生成的内容永远不会自动覆盖人工写的内容。

版本规则是这个产品的审计基础。你可以这样理解：章节正文像一份合同，每次修改都要签一份新合同，旧合同永远保留，不能涂改。

#### 动手之前，先弄懂几个词

**富文本编辑器**：可以设置标题、加粗、列表、表格的编辑器。本项目使用 Tiptap。

**受限 Schema**：我们对编辑器允许的内容做限制，只允许标题、段落、列表、表格和少量格式，不允许任意网页代码、外链图片和脚本。这样既安全，也保证导出时格式可控。

**block_id**：给正文里的每个可引用节点分配一个稳定编号。引用记录的是"某个正文块引用了某个资料块"，所以正文块需要编号。

**不可变版本**：版本一旦创建就不能修改。修改内容必须创建新版本。

**选定版本（selected version）**：章节当前使用的那一版。章节记录一个指针，指向它。

**采用（select）**：用户明确选择某一版作为章节当前使用的版本。采用历史版本或者 AI 候选版本，都要通过这个动作。

**内容比较**：把两个版本的内容做成"新增了什么、删除、修改了什么"的清单。

#### 具体怎么做

**第一步：写章节版本的数据库迁移。**

创建章节版本表、版本要求响应表、引用表。字段对照 [数据库文档.md](./数据库文档.md) 第 8 节。版本表没有"更新时间"字段，因为正文不允许被更新。

**第二步：实现服务端内容校验。**

服务端必须再次检查客户端提交的内容：节点类型是否在白名单里、嵌套深度是否超标（不超过十二层）、总字数是否超限（不超过十万字）、请求体是否过大、每个节点的编号是否唯一。检查通过之后，派生纯文本内容和内容哈希，一起保存。

客户端检查只是为了让用户早点知道错误，服务端检查才是真正的防线。

**第三步：实现保存和采用接口。**

保存的语义是：创建新版本并立即采用，必须带章节版本号防止并发覆盖。采用接口的语义是：显式选择某一版为当前版本，也必须带版本号。两种动作都会把章节标记为"需要复核"，而且不删除历史审核记录。

AI 生成走的是另一条路径：只创建候选版本，**不动当前采用的内容**。

**第四步：实现引用。**

引用由四个字段组成：正文块编号、来源块编号、被支持的主张、支持状态。客户端不能自己填写页码，页码由服务端根据来源块反查。每个引用都要检查：正文块是否存在、来源块是否属于本项目或者组织共享资料、资料版本是否在相关基准范围内。

没有引用的人工段落要如实标注为人工内容，不能假装它有来源。

**第五步：实现比较接口。**

传入两个版本，返回块级别的差异。两个版本必须属于同一个章节。比较结果在界面上的展示方式后面可以优化，第一版只要能看出"哪里多了、哪里少了、哪里改了"就够。

**第六步：写前端章节工作台。**

第一版做成三栏布局：左边是章节目录树，中间是编辑器，右边是要求列表、引用列表、问题面板和版本列表。工具栏只保留允许的格式按钮。

**第七步：认真处理保存冲突。**

当用户保存时版本号已经过期，界面要显示"服务器上的版本已经更新"，并且提供三个选择：查看差异、复制我的草稿、放弃我的修改。**绝对不能静默用服务器的内容覆盖用户正在写的内容**，那是用户最不能接受的体验。

**第八步：补测试。**

- 非法节点、超深、超长、重复编号的内容全部被拒绝。
- 两个请求带同一个版本号保存，只有一个成功，另一个返回冲突，且本地草稿不丢。
- AI 生成的候选版本不会改变当前采用的内容。
- 采用候选版本之后，章节标记为需要复核。
- 比较接口的输出正确。
- 引用指向其他项目或者不存在的块时被拒绝。

#### 怎么算做完了

- [ ] 浏览器里能完成：查看候选版本、查看证据、采用、手工修改、比较两个版本、回退到旧版本。
- [ ] 数据库中找不到任何正文更新操作留下的痕迹（所有修改都是新增版本）。
- [ ] 冲突场景演示一遍，本地草稿没有丢失。

#### 常见问题和提醒

**不要用纯文本反推富文本结构。** 保存时必须保存结构化的 JSON，纯文本只是派生出来的辅助数据。

**不要把编辑器生成的网页代码直接存进数据库。** 那等于允许任意代码进入系统，是安全漏洞。

**冲突时不要简单地"以服务器为准"。** 用户花十分钟写的内容被一句话覆盖，是产品质量事故。

#### 这一步和企业开发的关系

版本控制、富文本的边界控制、并发冲突体验，是企业协作产品的核心难点。真实公司里这一块通常由前后端多人配合、迭代好几周完成。你做到"可用且不丢数据"就达到了第一版目标，不必追求和成熟产品一样精致。

### C5 规则检查与引用校验

**难度**：二星　**预计时间**：12 到 18 小时

#### 这一步要解决什么问题

内容里的问题分两种。第一种是确定性的错误，例如工期数字前后不一致、项目名称写错、引用的资料已经失效；第二种是需要理解才能判断的问题，例如"这段内容够不够针对本工程"。第一种适合用规则来检查，因为规则准确、可解释、可重复；第二种适合交给模型和人工。

这一步要把第一类检查做出来。规则引擎的能力看起来不炫，但它是整个质量体系里最可靠的一层。

#### 动手之前，先弄懂几个词

**规则引擎**：一组"如果满足某个条件，就报告一个问题"的检查逻辑。

**确定性**：同样的输入永远得到同样的输出。规则检查必须是确定的，不能引入随机因素。

**误报**：系统报告了一个实际上不存在的问题。

**漏报**：系统没有发现真正存在的问题。

**严重级别**：问题的严重程度，分阻断级、高、中、低。阻断级必须修正后重新检查，不允许人工绕过。

#### 具体怎么做

**第一步：实现五类规则。**

- 数值一致性：工期、金额、评分上限这些数字与基准里的数字对比。
- 项目名称一致性：正文里出现的项目名称与基准一致。
- 引用有效性：引用的来源块是否存在、资料是否被拒绝或者归档、许可是否还有效。
- 待补项检测：正文里有没有显式的待补标记或者空占位。
- 要求响应完整性：本章映射的每条要求，在章节里有没有对应的响应声明。

**第二步：输出统一结构的发现。**

每条发现包含：严重级别、类别、所属章节版本、关联要求、关联正文块、证据、修改建议、当前处置状态。这一版先存在任务的步骤结果里，到 D2 步骤再落进正式的审查发现表。

**第三步：接入生成流程。**

规则检查的发现要进入"有限修订"节点，让模型有机会改掉问题。修订之后重新检查一遍，最多两轮。两轮之后如果问题还在，保留问题并如实展示，不隐瞒。

**第四步：在界面上展示。**

在章节工作台右侧增加一个问题面板，按严重级别排序。点击一条问题能定位到对应的正文块。阻断级的问题要有明显的视觉标识，并且标明"必须修正后重新检查"。

**第五步：写正反两组测试。**

- 注入一个工期冲突的样本，能检出阻断级问题。
- 注入一个项目名称写错的样本，能检出。
- 注入一个引用资料被拒绝的样本，能检出引用失效。
- 用一段没有问题的真实文本做回归，确认不会产生误报。
- 同一段内容检查两次，结果完全一致。

#### 怎么算做完了

- [ ] 规则引擎的单元测试覆盖率不低于百分之八十。
- [ ] 三类人造问题全部被检出，并且定位准确。
- [ ] 真实文本样本上的误报情况有记录，写进 PR 描述。

#### 常见问题和提醒

**不要把"没有发现问题"当成"内容合格"。** 规则只覆盖确定性维度，语义问题要靠后面的审查。

**不要在规则里偷偷调用模型。** 那样规则就不可解释了，也会变得又慢又贵。

#### 这一步和企业开发的关系

生产系统里有一条重要原则：能用规则解决的，绝不交给模型。因为规则便宜、快、可解释、可回归。企业里会把规则沉淀成规则库，随着业务经验不断积累。

## 第 7 章 阶段四：审查、审核与导出（D1 到 D4）

**这个阶段的目标**：把 AI 生成的草稿变成"可以提交的成果"。系统负责发现问题和风险，人工负责判断和处置，审核人员负责放行，最后导出成 Word 文件。做完这个阶段，你会第一次体验"两个角色配合"的完整业务闭环。

**这个阶段的关键词是"留痕"**：谁发现了什么问题、谁基于什么理由放过了它、谁在什么时候批准了哪个版本，全部要能查得到。

| D2 | 审查报告与问题处置 | 二星 | 14 到 20 小时 | 报告冻结目标版本，问题处置有规则有留痕 |

### D1 语义审查与重点章节

**难度**：三星　**预计时间**：18 到 26 小时

#### 这一步要解决什么问题

规则检查只能发现确定性的错误。那些需要"读懂内容"才能判断的问题，例如"这段施工方案有没有回应评分项""这段结论有没有证据支撑""这段内容是不是针对本工程的"，需要交给模型来做对照审查。

这一步要做的不是"让模型点评一下"，而是把审查拆成可检查的维度，让模型输出结构化的结论，这样程序才能统计、回归和展示。

#### 动手之前，先弄懂几个词

**语义审查**：让模型对照要求和证据，检查内容是否完整、是否针对、是否有依据。

**要求响应状态**：每条要求的响应情况，分四种：完整响应、部分响应、没有响应、需要补充确认。

**证据支持**：正文里的一个结论，能不能被引用的资料内容支撑。

**盲评**：把两段来源不同的内容去掉标记后让行业人员打分，用来对比质量。它比"自己觉得好"可信得多。

#### 具体怎么做

**第一步：为每类重点章节写审查提示词。**

先从施工方案、进度安排、质量保证、安全文明施工、资源配置这五类里选三到五类。每一类写一份审查提示词，内容包含：要检查的维度、必须返回的字段和格式、禁止行为（例如不能编造规范、不能给出正式分数）。

**第二步：定义统一的输出结构。**

每条要求的响应状态要有明确取值；每个发现要有严重级别、类别、涉及的正文块、涉及的要求（可以没有）、原文依据、修改建议。模型返回之后必须做结构校验，校验失败走修复流程。

**第三步：守住三个边界。**

第一，规范引用只能来自已上传并且已确认的资料，系统不做法律或规范适用性的自动判断。第二，响应状态只是建议，不是正式评标分数，界面上也要这样写。第三，审查不能访问基准之外的资料。

**第四步：准备带已知问题的评测样本。**

每类章节准备一到两份样本，故意放入已知问题：漏掉一个评分项的响应、写了一个没有证据支撑的结论、引用了一条被撤销许可的资料、明显写了另一个项目的内容。把"应该检出什么"写成标注清单。

**第五步：跑第一轮评测并如实记录。**

记录检出情况、误报情况、失败案例，写清楚使用的样本、日期和模型模式（模拟还是云端）。**不美化、不虚构**。如果只检出四类问题中的三类，就写三类，并分析为什么第四类没检出。

**第六步：接入生成流程。**

把语义审查接到 C2 的审查节点上，规则发现和语义发现使用同一套展示结构，让用户在一个面板里看到全部问题。

#### 怎么算做完了

- [ ] 四类注入问题中至少检出三类。
- [ ] 每条问题都能定位到正文块和来源。
- [ ] 审查运行的成本可以在运行详情里看到。
- [ ] 第一版评测记录完成，写清楚样本、日期和模式。

#### 常见问题和提醒

**让模型自由输出一段点评**是最常见的错误，结果无法程序化处理，也无法做回归对比。

**提示词不版本化**也会出问题：改完之后不知道效果是变好还是变差。

**不要把响应状态展示成"中标概率"**，这是对用户的误导，也可能带来合规风险。

#### 这一步和企业开发的关系

企业里把这一步叫"评测集加回归"。模型升级、提示词调整之后，必须重新跑一遍评测，防止质量悄悄下降。这是 AI 产品质量管理的标准做法。

### D2 审查报告与问题处置

**难度**：二星　**预计时间**：14 到 20 小时

#### 这一步要解决什么问题

审查会产生很多问题，这些问题需要有正式的记录：属于哪份报告、针对哪个版本、什么严重级别、谁处理的、为什么这样处理。而且要保证一件重要的事情：**报告一旦完成，它的目标版本就冻结了。** 用户之后修改内容，不会影响这份报告的结论。

#### 动手之前，先弄懂几个词

**审查报告**：一次审查运行的成果，记录它检查了哪些章节版本、对应哪个基准、发现了哪些问题。

**发现（Finding）**：报告里的一条问题，包含严重级别、类别、证据、建议和处置状态。

**冻结目标**：报告记录的是"检查时的那几个版本"，之后版本怎么变都不影响它。

**最新有效报告**：审核一个版本时，必须使用覆盖这个版本和基准的、最新完成的那份报告。不能拿一份旧报告绕过新发现的问题。

#### 具体怎么做

**第一步：写审查相关的数据库迁移。**

创建报告表和发现表。字段对照 [数据库文档.md](./数据库文档.md) 第 10.1 到 10.2 节。注意发现表有一个约束：阻断级的问题状态只能是"未处理"。

**第二步：实现审查运行。**

发起审查时冻结章节版本清单和基准编号，一到五十个版本，不能跨项目或者跨基准。运行期间用户切换了版本，不影响这份报告的目标。

报告完成时，把"仍然采用这些目标版本"的章节标记为需要复核。为什么要这样做？因为新报告可能发现了问题，之前的审核结论需要重新确认。

**第三步：实现报告和发现接口。**

提供报告列表、报告详情、发现列表、发现处置四个接口。发现列表支持按严重级别和状态过滤。

**第四步：实现处置规则。**

- 阻断级问题：任何人工处置都拒绝，只能修改内容后重新审查。
- 高级问题：只能标记为"接受风险"，并且必须写理由。
- 中级和低级问题：可以标记为"已解决"或者"接受风险"，都必须写理由。
- 处置只改变状态和说明，**不能修改检查结论的原文**。

**第五步：实现"最新有效报告"的判断函数。**

判断逻辑是：在所有已经完成、覆盖目标版本和基准的报告里，按完成时间排序，取最新的一份。这个函数要写成公共函数，审核和导出都调用它，不能各写一套，否则很容易不一致。

**第六步：补测试。**

- 报告完成之后用户修改章节，报告的目标不变，新报告成为最新报告。
- 用旧报告去审核，被拒绝。
- 阻断级问题处置被拒绝；高级问题只能接受；理由缺失被拒绝。
- 两个人同时处置同一条发现，只有一个成功。

#### 怎么算做完了

- [ ] 界面上能完整展示报告、问题、处置记录。
- [ ] 上面四条测试全部通过。
- [ ] 数据库里能查到报告和发现的关联，相关记录不能被随意删除。

#### 常见问题和提醒

**报告如果引用"当前版本"而不是冻结版本**，用户一编辑，报告的语义就变了，这在审计上是不允许的。

**处置不记录操作者和理由**，等于没有留痕，将来没人知道当时为什么放过这个问题。

**"已解决"和"接受风险"不能混为一谈。** 前者表示问题被修好了，后者表示知道有风险但选择承担，这两种情况的责任完全不同。

#### 这一步和企业开发的关系

审计与合规、问题闭环管理是企业软件的基本要求。"谁在什么时间、基于什么理由、放过了什么问题"必须能够复盘，这在金融、医疗、政企项目里是硬性规定。

### D3 审核与双角色协同

**难度**：二星　**预计时间**：12 到 18 小时

#### 这一步要解决什么问题

内容改好了、问题也处理了，最后需要一个人正式批准："这个版本可以用于提交。"在真实企业里，这一步必须由别人来做，因为自己检查自己不可靠。这个原则叫做"四眼原则"。

这一步要实现完整的审核流程：编写者提交、审核者审核、条件全部满足才能通过、每次动作都留下记录。

#### 动手之前，先弄懂几个词

**审核（Approval）**：对某个具体版本的正式放行。

**四眼原则**：重要决定必须经过两个人确认，一个人不能既做又审。

**自审**：审核自己创建的内容。本项目禁止，管理员也不例外。

**请求修改**：审核者不通过，并写明需要改什么。

**有效结论**：同一个版本可能被审核多次，例如先通过、后来又被要求修改。判断"当前是否有效"时，取符合条件的最新一条记录。

#### 具体怎么做

**第一步：写审核记录的数据库迁移。**

创建审核记录表。这张表是追加式的：只能新增记录，不能修改已有记录。字段对照 [数据库文档.md](./数据库文档.md) 第 10.3 节。

**第二步：实现审核接口。**

通过审核之前，要一次性检查所有条件：当前基准有效且没有脏标记；版本仍然是章节的当前采用版本；有覆盖这个版本和基准的最新完成报告；没有待补项；没有无效或者待确认的引用；没有未处理的阻断级和高级问题；审核者不是这个版本的创建者。

任何一个条件不满足，都要返回明确的错误码和可读的原因，不能只说"审核失败"。

**第三步：实现请求修改。**

请求修改必须写意见，写完之后把章节标记为需要复核，但**不修改正文**。审核者的职责是判断，不是替编写者改内容。

**第四步：处理重复提交。**

审核接口要求幂等键。重复提交同一个审核请求，返回原结果，不产生第二条记录。

**第五步：实现有效结论判定。**

写一个公共函数：同一个版本可能有多条审核记录，取符合基准和报告条件的最新一条作为当前结论。后来的"请求修改"会让之前的"通过"失效。

**第六步：写前端审核页面。**

页面展示：待审核的版本、对应的基准、最新的报告摘要、未解决的问题、审核意见输入框和两个按钮（通过、请求修改）。**编写者视角看不到审核按钮**，界面上要明确当前登录者的角色。

**第七步：用两个账号完整演示。**

编写者账号：生成内容、修改、发起审查。审核者账号：查看问题、处置、审核通过。再切回编写者账号查看状态。整个过程不允许手工修改数据库。

**第八步：补测试（负面优先）。**

- 自己审自己，被拒绝（包括管理员自审）。
- 审核之后创建新版本，旧审核不再支持新版本。
- 基准变化之后，旧审核失效。
- 存在未处理的高级问题，拒绝通过；高级问题被接受之后，可以通过。
- 存在阻断级问题，拒绝通过，无论问题处于什么状态。
- 重复提交同一个审核请求，幂等，不产生第二条记录。

#### 怎么算做完了

- [ ] 上面六条测试全部通过。
- [ ] 双角色演示全程没有手工改数据库。
- [ ] 审计日志里能看到审核相关的动作。

#### 常见问题和提醒

**只在接口层做自审判断是不够的**，服务层和数据库层也要有第二道防线，防止将来有人从别的入口绕过接口。

**审核条件的检查代码不能散落在多个地方**，否则改了一条规则，另一个地方还是旧的。要集中到一个函数里。

**不要用时间戳裸比较来判断"最新"**，要按设计文档规定的排序字段来取。

#### 这一步和企业开发的关系

四眼原则和职责分离是金融、政企项目的标准合规要求。面试时你能讲清楚"为什么管理员也不能自审"，说明你理解的是制度设计，而不只是功能实现。

### D4 DOCX 导出与提交草稿

**难度**：三星　**预计时间**：18 到 26 小时

#### 这一步要解决什么问题

系统的最终产物是 Word 文件。这一步要把章节内容渲染成可编辑的 DOCX，并且严格区分两种导出：审阅版可以包含未审核的内容，供内部查看；提交草稿必须满足全部审核条件，才能用于对外提交。

还有一个重要机制：导出之后如果数据发生变化，这份导出就"过期"了，系统在下载时会再次检查并拒绝，避免有人拿旧文件当新成果用。

#### 动手之前，先弄懂几个词

**模板**：导出的固定格式，包括纸张、字体、标题样式、页边距。第一版使用一个固定模板，名字叫 `technical-v1`。

**渲染**：把结构化的章节内容转换成 Word 文档里的段落、标题和表格。

**导出快照**：记录这次导出包含哪些章节、哪个版本、哪个基准、依据哪份审核记录。

**审阅版**：保留来源说明、未解决问题和待补项的版本，文件上要有明显的草稿标记。

**提交草稿**：满足全部审核条件的版本，是当前可以对外使用的成果。

**导出过期**：导出之后，基准、版本、审核或者资料许可发生变化，导致这份导出不再有效。

#### 具体怎么做

**第一步：写导出相关的数据库迁移。**

创建导出记录表和导出条目表。条目表冻结章节版本、顺序、标题快照和审核依据。字段对照 [数据库文档.md](./数据库文档.md) 第 11.1 到 11.2 节。

**第二步：实现内容渲染。**

把允许的节点逐个映射成 Word 里的元素：标题层级对应标题样式，段落对应正文，加粗斜体下划线对应字符格式，列表对应项目符号或者编号，表格对应表格。中文字体、纸张和页边距来自固定模板。

**第三步：实现两种模式的差异。**

审阅版允许未审核内容，要求每个章节都有选定的版本，文件里保留引用摘要、未解决问题和待补项。提交草稿要先做一次严格检查：基准当前有效、所有选定版本都获得独立审核、没有待补项、没有需要复核的标记、没有未处理的阻断级和高级问题。不满足就返回可读的问题清单。

**第四步：把导出做成后台任务。**

导出可能耗时几十秒，所以要复用 A8 的任务框架。导出任务的幂等键是导出记录编号。失败重试之前先检查对象存储里是不是已经有同一份产物，避免重复生成。

**第五步：实现下载时的再次检查。**

下载提交草稿时，重新检查基准、选定版本、审核记录和资料许可。任何一项不满足，返回"导出已过期"。历史审阅版仍然可以下载，但要标注它是历史快照。

**第六步：测试和人工检查。**

- 自动检查生成文件的结构：标题层级、列表、表格、中文字体设置。
- 人工用 Word 或者 WPS 打开，检查目录层级、字体、表格边框，并截图存证。
- 有未审核内容时，提交草稿被拒绝。
- 导出之后修改章节，下载提交草稿返回"已过期"。
- 重复用同一个幂等键创建导出，不产生第二份记录。

#### 怎么算做完了

- [ ] 审阅版和提交草稿各导出一份，人工检查通过。
- [ ] 上面五条测试全部通过。
- [ ] 导出记录页面能看到来源版本、审核依据、状态和是否过期。
- [ ] 你清楚第一版不承诺什么，例如所有投标平台的格式兼容、复杂模板的完全还原。

#### 常见问题和提醒

**"文件能打开"不等于"格式合格"。** 中文字体、分页和表格样式必须人工核对，这是文档类产品的常识。

**导出不能使用"当前版本"**，必须使用创建导出时冻结的版本。

**不要忘记检查资料许可。** 如果一份资料的许可在导出后被撤销，下载时必须拒绝，否则会把不该外发的内容交出去。

#### 这一步和企业开发的关系

文档生成和快照合规是审计型系统的标准做法。企业里还会加上文件指纹、水印、下载审计、有效期管理，但核心逻辑就是"导出即冻结、下载再校验"。

### E1 可观测性与健康检查

**难度**：二星　**预计时间**：12 到 18 小时

#### 这一步要解决什么问题

系统跑在服务器上，你看不见它。当用户反馈"生成卡住了"或者"页面很慢"，你需要有能力回答：是哪个环节慢？后台任务排队了吗？模型调用失败了吗？数据库连接正常吗？

这一步要给系统装上"仪表盘"，让它在出问题的时候能告诉你发生了什么，而不是靠猜。

#### 动手之前，先弄懂几个词

**日志**：程序运行过程中记录的文字信息。结构化日志指的是用固定格式（例如 JSON）记录的日志，方便程序自动检索和分析。

**指标**：可以累加和统计的数字，例如任务成功率、平均等待时间、错误次数。指标适合看趋势和触发告警。

**追踪**：把一个请求经过的所有环节串起来，例如从浏览器请求开始，到数据库查询、后台任务、模型调用，用的是同一个追踪编号。追踪适合排查"慢在哪一步"。

**健康检查**：给运维系统用的接口，用来判断服务是否存活、依赖是否正常。

**告警**：当指标超过某个阈值时主动通知人。例如"五分钟没有收到工人进程的心跳"。

**标签基数**：监控指标上可以附加标签，但标签的取值数量要有限。如果把每个组织编号都当成标签，指标数量会爆炸，监控系统会被拖垮。

#### 具体怎么做

**第一步：改造日志。**

所有日志改成结构化格式，请求日志和任务日志共享三个编号：请求编号、运行编号、追踪编号。同时写一条自动化测试，专门验证日志里不会出现密码、会话凭证、密钥、完整原文和完整提示词。

**第二步：接入追踪。**

给 Web 框架、数据库访问、后台任务加上自动追踪。本地开发可以先输出到控制台，演示环境再接入正式的追踪服务。

**第三步：定义关键指标。**

至少要包含：任务成功率、排队等待时间、待投递表里最旧记录的存在时长、租约恢复次数、工人进程心跳、模型限流和超时次数、未知费用预留数量、普通接口的响应时间分位数。普通请求和长任务的指标要分开统计，不能混在一起。

**第四步：实现三个健康检查接口。**

存活检查只回答"进程还在吗"，对外公开。就绪检查回答"数据库、迁移版本、必要存储都正常吗"，只给内网探针用。指标接口只允许内网访问。消息队列临时不可用时，可以标记为"降级"，但不要因此重启服务。

**第五步：配置初始告警规则。**

先定义四条：五分钟没有工人进程心跳；待投递表里最旧的记录超过两分钟；任务排队超过五分钟；连续出现模型调用失败。阈值以后可以调整，但每次调整都要留下记录。

**第六步：控制指标标签。**

组织编号、运行编号这类高基数的值只放进日志和追踪，不要作为监控指标的标签。

**第七步：加一个可选的监控面板。**

在容器编排配置里增加一个可选的监控配置组，包含指标收集和可视化面板，按需启动，不要拖慢日常开发。

**第八步：给事件推送加保护。**

同一个账号对同一个运行最多保持五条事件推送连接，超限返回限流错误。每次读取事件使用短事务，不要因为连接多就把数据库连接池占满。

#### 怎么算做完了

- [ ] 跑完一次完整的生成任务，能在日志和追踪里用同一个追踪编号串起全链路。
- [ ] 手动停掉工人进程，五分钟内告警规则生效（本地用脚本模拟即可）。
- [ ] 日志脱敏测试通过：搜索日志文件，找不到测试用的密钥和完整原文。
- [ ] 数据库断开时就绪检查返回失败，恢复后自动变回正常。

#### 常见问题和提醒

**日志里打印完整请求体**是最隐蔽的泄密重灾区，特别是资料上传和模型调用，必须做脱敏。

**指标标签不要用高基数值**，否则监控系统会先于业务崩溃。

**健康检查不要调用有费用的模型**，否则探针会一直花钱。

#### 这一步和企业开发的关系

可观测性是运维的基础，也是评审一个服务能不能上线的必要条件。企业里有一句话：不能被观测的系统，等于不能运维的系统。

### E2 CI/CD 与发布流程

**难度**：二星　**预计时间**：14 到 20 小时

#### 这一步要解决什么问题

前面你已经有了最小版本的 CI。这一步要把它补完整，并且建立一套可重复的发布流程：从代码合并，到构建镜像，到执行数据库迁移，到部署，到验证，每一步都有明确的顺序和失败处理。目标是把"发布"从一件需要小心翼翼的事情，变成一件例行公事。

#### 动手之前，先弄懂几个词

**CI（持续集成）**：每次提交代码都自动运行检查。

**CD（持续交付或者持续部署）**：在 CI 通过之后，自动或者半自动地把新版本部署出去。

**镜像**：打包好的程序运行环境，带着版本号。

**环境**：同一套程序在不同用途下的部署，例如本地开发环境、测试环境、公网演示环境、生产环境。

**迁移任务**：部署过程中单独执行数据库迁移的步骤。它必须和应用部署分开，因为迁移失败时应用不应该带病启动。

**冒烟测试**：部署完成之后，立刻验证最关键几条路径是否正常。

**回滚**：出问题时把应用切换回上一个版本。

#### 具体怎么做

**第一步：补全 CI。**

后端：代码风格检查、类型检查、单元测试、集成测试（流水线里启动真实的数据库和 Redis）。前端：代码检查、类型检查、构建。迁移：验证空库能升级、上一个发布版本也能升级。容器：构建镜像，使用固定基础镜像并记录摘要，产物带版本号。

**第二步：建立环境配置规则。**

所有配置通过环境变量注入。本地、测试、演示使用独立的配置文件或者密钥。**任何环境都不允许把真实密钥提交到仓库。**

**第三步：写发布脚本。**

发布流程按固定顺序：备份并验证迁移、拉取固定镜像、执行迁移任务、部署应用、运行冒烟测试、观察错误和积压。数据库的破坏性变更采用"先扩展、再迁移数据、最后清理旧结构"的分步方式，不要一步到位。

**第四步：明确回滚方案。**

应用镜像可以回退到上一个版本，但**数据库结构不会自动回退**。所以发布前要确认：上一个版本的应用能兼容新的数据结构。这就是"扩展、迁移、收缩"三步法的意义。

**第五步：在本地演练一次完整发布。**

用同一套容器配置和脚本，在本地走一遍完整发布，包括故意制造一次失败并回滚。演练之后，把过程记录写进 `docs/releases/`。

**第六步：建立发布记录。**

每次发布写一页记录：版本号、日期、包含哪些变更、有没有数据库迁移、验证结果、回滚点在哪里。

#### 怎么算做完了

- [ ] 主分支保护开启，PR 上 CI 全绿才能合并。
- [ ] 有一次"发布、冒烟、故意失败、回滚"的完整演练记录。
- [ ] 迁移任务和应用部署是分开的，迁移失败时应用不会启动。
- [ ] 用搜索命令确认仓库里没有任何真实密钥。

#### 常见问题和提醒

**应用启动时自动执行迁移**是常见错误。如果同时启动多个实例，它们会同时尝试迁移，造成数据损坏。

**回滚只回代码、不回配置**也会出问题。配置和代码要作为一个整体版本管理。

**演示环境不要复用生产密钥。**

#### 这一步和企业开发的关系

持续集成和持续交付是工程成熟度的直接体现。面试官问"你的项目怎么发布"，如果你能讲清楚"迁移和应用分开、发布前备份、失败怎么回滚"，说明你理解的是工程，不只是写代码。

### E3 评测与压测

**难度**：三星　**预计时间**：20 到 30 小时

#### 这一步要解决什么问题

"效果不错"是一种感觉，"准确率百分之八十七"是一个数字。这一步要把感觉变成数字，并且如实说出数字的适用范围和局限。

评测分两部分。业务评测衡量内容质量，例如要求抽取是否完整、检索能不能找到正确证据、引用是否支持结论。性能压测衡量系统在多人同时使用时的表现。

#### 动手之前，先弄懂几个词

**评测集**：用来衡量质量的一组固定样本和标准答案。

**调试集和保留集**：调试集用来反复调整，保留集只在最后用一次。同一个项目的页面不能同时出现在两边，否则等于提前看过答案。

**指标**：用数字表示质量，例如抽取召回率、前十名命中率、引用支持率。

**基线对照**：用普通提示词直接生成作为参照，和 Harness 的输出对比。对照必须使用同样的模型、同样的样本和同样的成本口径。

**分位数（P95）**：百分之九十五的请求耗时低于这个数值。它比平均值更能反映真实体验，因为平均值会被少数极快或者极慢的请求带偏。

#### 具体怎么做

**第一步：准备评测数据。**

样本清单记录授权状态、脱敏方式、工程类型、文件指纹和数据划分。标注内容包括要求、事实、来源位置、问题与证据的对应关系、响应状态和典型错误。目标规模是至少五个独立项目；如果真实材料不够，就用模拟样本，并在报告里明确说明。

**第二步：跑指标。**

至少要算：要求抽取的召回率和准确率；检索前十条命中率；引用位置可打开比例；引用支持率抽样；生成、人工复核、修改、导出的分项耗时。

**第三步：做基线对照和盲评。**

用同样的供应商、模型和样本，对比普通直接提示和 Harness 的输出，记录质量差异和成本差异。盲评时打乱两段内容的顺序，评分维度包括针对性、完整性、可执行性和事实可靠性。

**第四步：做性能压测。**

用二十个并发用户测试普通接口和列表接口，记录服务器配置、数据量、请求组合和响应时间分位数。长任务的排队、执行和总耗时单独统计，不要混进普通接口的指标里。

**第五步：写报告，并且如实标注。**

报告里必须写清楚：使用的是模拟模式还是云端模式；提示词版本、基准版本、模型和索引配置；样本数量和使用范围；哪些指标达标、哪些没有达标、哪些根本没有测量。

#### 怎么算做完了

- [ ] 至少一份完整的业务评测报告和一份性能报告，都包含失败案例章节。
- [ ] 报告能让不懂这个项目的人看懂，指标定义写得很清楚。
- [ ] 你能在三分钟内讲清楚：哪些指标达标、哪些没有、原因是什么。

#### 常见问题和提醒

**把调试集上的数字当成最终结论**是自欺欺人。保留集的存在就是为了防止这种自我欺骗。

**样本太少就下结论**也不可信。样本不足时应该写"样本量小，结论仅供参考"，而不是硬给一个百分比。

**把模型自己的评分当作人工评测结果**也不行，两者必须分开记录。

#### 这一步和企业开发的关系

质量度量和对外的报告口径是企业软件的基本功。"不夸大、不隐瞒"是技术公信力的来源，也是面试里最能体现成熟度的地方。

### E4 备份恢复与故障演练

**难度**：三星　**预计时间**：16 到 24 小时

#### 这一步要解决什么问题

只要系统里有真实数据，就一定会有人问两个问题："数据丢了怎么办？""系统坏了多久能恢复？"这一步要用实际行动回答这两个问题：写备份脚本、写恢复脚本，然后亲手把系统弄坏几次，验证真的能恢复。

这是个人项目里极少有人做、企业里必须做的事。做完之后，你在面试里能讲的东西会比别人多一个量级。

#### 动手之前，先弄懂几个词

**一致性备份**：备份出来的数据在时间点上是一致的。如果一边有人写数据一边备份，数据库和文件之间可能对不上，所以要先暂停写入，再备份。

**备份清单**：记录这次备份包含哪些东西、版本是什么、校验和是多少。恢复的时候照着清单核对，缺一件都不行。

**恢复演练**：真的从备份恢复到一套空环境里，验证数据可以用，而不是只确认"备份文件存在"。

**RTO 和 RPO**：RTO 是从故障到恢复需要多长时间；RPO 是最坏情况下会丢多少数据。这两个数字必须靠演练测量出来，不能拍脑袋填写。

**故障注入**：故意制造故障，例如杀掉进程、重启中间件、断开网络，观察系统的表现。

#### 具体怎么做

**第一步：写备份脚本。**

脚本按固定流程执行：暂停写入请求和投递程序；等待正在执行的任务结束或者安全取消；备份数据库；备份对象存储；备份文档模板和配置版本；生成备份清单，包含编号、时间、文件列表、校验和、数据库迁移版本和应用镜像版本。

**第二步：写恢复脚本，并且恢复到空环境。**

恢复顺序是：先恢复对象存储，再恢复数据库，然后使用相同的模板和解析配置；检查文件引用是否都能对上；用只读方式启动接口验证；清理旧的租约并递增代际号；最后恢复投递和写入。

恢复完成之后必须做一件事：**撤销所有登录会话。** 因为旧的会话凭证可能已经泄露到系统之外，恢复之后必须让所有人重新登录。此外，未确定用量的模型调用保留为未知状态，待投递的任务允许重放，靠幂等保证不产生重复结果。

**第三步：做五次故障演练。**

每次演练写一页记录，包含假设、步骤、观察到的现象、结论和遗留问题。五次演练的内容是：

1. 杀掉工人进程，验证租约过期后自动恢复，并且不产生重复结果。
2. 重启消息队列，验证业务状态不丢，排队任务能恢复投递。
3. 模拟模型超时或者断网，验证未知用量状态正确，恢复后不会重复外发。
4. 模拟数据库迁移失败，验证应用能回滚，数据没有被破坏。
5. 从备份恢复到空环境，验证引用能打开、流程能继续。

**第四步：测量并记录恢复指标。**

记录每次演练实际花费的时间。测出来多少就写多少，没有测量就写"未测量"。不要为了让报告好看而编造数字。

**第五步：把备份放到不同的故障域。**

只把备份复制到本机的另一个目录，不算灾难恢复。如果整台机器坏了，两个目录会一起丢。备份至少要放到另一块磁盘、另一个存储服务或者另一台机器上。

#### 怎么算做完了

- [ ] 五次演练记录齐全，每页都有观察和结论。
- [ ] 恢复演练之后，能完整演示"登录、查看项目、打开引用、继续生成"。
- [ ] 备份和恢复脚本都有试运行模式，误操作有阻挡。
- [ ] 备份放在不同的故障域，不只是本机另一个目录。

#### 常见问题和提醒

**只备份数据库、不备份文件存储**，恢复之后所有引用都会断开，等于白恢复。

**恢复之后不撤销会话**，等于把旧钥匙留在了门上。

**把"备份成功"当成"恢复可用"**，是灾难恢复里最危险的错觉。必须实际恢复一次。

#### 这一步和企业开发的关系

灾难恢复和业务连续性是运维的核心职责。企业里会定期做恢复演练，并且把 RTO 和 RPO 写进服务承诺。你亲手做过一次，和别人只听说过概念，是完全不同的两回事。

### E5 公网演示与交接

**难度**：二星　**预计时间**：12 到 20 小时

#### 这一步要解决什么问题

最后一步有两个目的：让陌生人十分钟内看懂这个系统；让"下一个接手的人"（可能就是几个月后的你）能继续开发。

这一步的产出不只是软件，还有演示视频、交接文档和一套清晰的求职材料。

#### 动手之前，先弄懂几个词

**演示环境**：专门用来给别人看的部署，配置和真实生产分开。

**演示脚本**：一份"点什么、说什么、预期看到什么"的台本。它保证演示过程流畅、不遗漏重点。

**交接文档**：说明系统实现了什么、没实现什么、怎么启动、怎么恢复、已知问题是什么。

#### 具体怎么做

**第一步：搭建演示环境。**

按照设计文档里的服务清单部署：前端、接口、投递程序、工人进程、数据库、消息队列、文件存储，加一个反向代理提供加密访问。监控面板作为可选项。**关闭公开注册**，只保留预置的演示账号。

**第二步：守住演示数据的纪律。**

公网演示环境只允许使用可以公开的模拟资料。真实的企业资料、真实的项目信息，一律不允许出现在公网演示环境。使用模拟模型运行，或者使用单独的演示密钥，界面上明确标注当前模式。

**第三步：写演示脚本并彩排。**

按照主流程写台本：登录、建项目、上传、解析、确认、发布基准、生成（包含一次暂停和恢复）、审查、切换审核账号、审核、导出 Word。**至少完整彩排三次**，因为很多环境问题只有在完整走流程时才会暴露。

**第四步：录制演示视频。**

录一段五到十分钟的视频，完整覆盖上面那条流程。视频里要包含一次真实的失败提示和恢复过程，这比全程顺利更能体现系统的可靠性。

**第五步：写交接文档。**

文档至少包含：哪些能力已经实现；哪些只提供了配置但没有真实使用过；哪些指标还没有测量；实际使用的依赖版本；怎么复现测试；怎么恢复备份；已知的限制和后续计划。README 要更新到"新人三十分钟能本地跑起来"的程度。

**第六步：整理求职材料。**

把 PR 列表、CI 记录、架构决策、评测报告、压测报告、演练记录和演示视频整理成一条叙事线：遇到什么问题、怎么解决、用什么证据证明解决了、还有什么没解决。

#### 怎么算做完了

- [ ] 公网地址可以访问，演示账号可以登录，注册入口已经关闭。
- [ ] 演示视频完整，包含一次真实的失败和恢复。
- [ ] 交接文档和 README 能让一个陌生人三十分钟内把系统跑起来。
- [ ] 任何一个设计决策，你都能指到对应的文档或者 ADR。

#### 常见问题和提醒

**演示当天才发现环境问题**是最常见的翻车方式，必须提前彩排。

**夸大没有实现的能力**，一旦被追问细节就会露馅。宁可说"这个还没做"，也不要说"这个做了但没演示"。

**不要把演示环境当成生产环境使用。**

#### 这一步和企业开发的关系

交付、知识转移和对外演示是工程师的软实力。能讲清楚"做了什么、没做什么、为什么"，是工程成熟度的最终体现。

## 第 9 章 卡住时的自救方法

### 9.1 卡住时的标准动作

遇到问题的时候，按下面的顺序自己走一遍。这个过程大概需要三十分钟，走完之后如果还没解决，就记录下来换个任务，明天再处理。

**第一，完整读一遍报错信息。** 从最后一行开始往上读。程序报错通常会把最直接的原因放在最后一行，把调用过程放在它上面。先找三个东西：错误类型、出错的文件、出错的行号。很多问题光靠读报错就能解决。

**第二，把问题缩小到最小复现。** 新建一个最小文件或者最小命令，去掉所有无关的代码，直到两种结果之一出现：问题必然出现，说明你找到了核心原因；问题消失了，说明原因在你刚去掉的那部分代码里。这个"缩小范围"的动作，是排查问题最重要的技能。

**第三，查官方文档。** 先查四份设计文档，再查相关技术的官方文档。查的时候注意版本号，中文博客和教程很可能是旧版本的写法。

**第四，精确搜索。** 把报错的英文原文复制到搜索引擎，去掉你项目里特有的路径和编号。不要用中文描述去搜索，因为报错信息的原文才是别人也遇到过的。

**第五，向 AI 提问。** 提问时必须带上五个要素：我想做什么、我运行了什么命令或者代码、完整的报错信息、我已经试过什么、我的环境是什么。缺少这些信息，答案就只能是泛泛而谈。

**第六，把问题写下来。** 记录在 `docs/questions.md` 里，写清楚"现象、已经排除的可能、下一步猜想"，然后去做别的小任务。不要为了一个问题耗掉一整个晚上。

### 9.2 常见故障速查

下面这张表列出了新手最常遇到的十几种问题。遇到的时候先在这里查一遍，通常能省下不少时间。

| 你看到的现象 | 可能的原因 | 先检查什么 |
|---|---|---|
| 提示找不到模块 | 命令没有通过项目自己的环境执行，装到了系统 Python 里 | 是不是用 `uv run` 执行命令；打印当前 Python 的实际路径 |
| 数据库连不上 | 容器没有启动、端口被占用、密码不对 | 查看容器状态和数据库日志，检查环境变量里的连接地址 |
| 迁移报"数据库不是最新状态" | 本地数据库版本落后 | 查看当前版本和历史版本，执行升级命令 |
| 集成测试互相影响 | 测试数据没有隔离 | 每个测试使用独立事务并回滚，测试库与开发库分开 |
| 后台任务不执行 | 工人进程没有启动、队列名字不对、消息格式不对 | 查看工人进程日志和启动参数 |
| 同一个任务执行了两次 | 消息系统只保证"至少一次投递" | 检查幂等键和"先查结果再执行"的逻辑 |
| 前端请求返回 404 | 代理没有配置，或者地址少了前缀 | 查看前端代理配置，打开浏览器网络面板看真实地址 |
| 前端写请求返回 403 | 缺少防跨站令牌，或者来源不合法 | 检查写请求有没有带令牌；检查前端和后端是不是同源 |
| Word 文件里中文乱码 | 模板字体缺失或者没有正确设置 | 检查生成环境里有没有安装许可允许使用的中文字体 |
| 本地能跑、CI 失败 | 环境版本或者变量不一致 | 对比 Node 和 Python 版本、锁文件、环境变量、时区 |
| 模型返回结构不符合要求 | 提示词、输出格式或者模型能力问题 | 保留原始响应（脱敏后），用同一输入重放，检查校验和修复逻辑 |
| 页面长时间没有响应 | 长任务写成了同步接口 | 检查是不是所有耗时工作都走了后台任务 |

### 9.3 什么时候该重构，什么时候该继续

重构的意思是"在不改变功能的前提下重新整理代码"。它很有价值，但如果时机不对，会变成拖延的借口。

| 你观察到的信号 | 应该怎么做 |
|---|---|
| 同一段代码被复制到第三个地方 | 立刻抽成公共函数，并补上测试 |
| 加一个字段需要改六个文件 | 停下来梳理数据模型，写一条 ADR |
| 测试要跑二十分钟而且经常失败 | 先修测试的可靠性，再继续新功能 |
| "先临时这样，以后再说"出现第三次 | 停下来还债，或者明确写进任务清单排期 |
| 功能还没做完就想换框架或者重写 | 不要换。把想法记下来，等这一阶段结束之后再评估 |

### 9.4 新手最容易犯的十个错误

**第一，想先把知识学完再开始做。** 你永远学不完，而且脱离项目学的知识很快就忘。正确的做法是最小前置加边做边学。

**第二，追求一次写对。** 正确的节奏是：先让测试失败，再让测试通过，最后把代码整理干净。写错再改是正常流程，不是失败。

**第三，跳过测试。** 前三个月你会觉得省了时间，第四个月开始每天还债，因为改动一个地方会弄坏另一个地方，而你根本不知道。

**第四，跳过文档同步。** 代码是写给机器执行的，文档是写给未来的你读的。两者缺一不可。

**第五，一口气写一个大功能。** 每个步骤内部也要拆成半天粒度的小任务，不然出错的时候你无法定位。

**第六，一上来就接真实模型。** 先用模拟模式把整条链路跑通，最后再换真实供应商。否则你分不清问题出在流程上还是模型上，还会白白花钱。

**第七，把密钥提交进仓库。** 一旦推送出去，就要当作已经泄露，必须立刻更换密钥，而不是简单删掉文件了事。

**第八，用没有授权或者没有脱敏的资料开发。** 这是合规事故，不是技术问题。使用模拟样本永远不丢人。

**第九，直接复制别人的整段代码。** 你能跑起来，但不知道它在做什么。面试官追问两句就会露馅。

**第十，不做学习笔记和复盘。** 每周花三十分钟复盘，效果抵得上多写一天代码。

### 10.2 本项目的业务术语

| 术语 | 完整解释 |
|---|---|
| 项目 | 一个具体工程的投标工作空间，所有资料和成果都挂在它下面。 |

| 发现 | 审查发现的一条问题，带严重级别和处置状态。 |
| 审核 | 对某个版本加基准加报告的正式放行记录。禁止审核自己创建的内容。 |
| 导出 | 冻结章节版本清单后生成的 Word 文件，分审阅版和提交草稿。 |
| 模拟模式 | 不调用云端的确定性假模型模式。所有模拟结果必须明确标注。 |

### 附录 B：Git 规范与 ADR 模板

**分支命名规则**：类型、编号、简短描述，用连字符连接。例如 `feat/a3-db-migration`、`fix/b2-scanned-pdf`、`docs/c1-model-gateway`、`chore/ci-cache`。

**提交信息格式**：`类型(范围): 摘要`。类型包括 feat（新功能）、fix（修缺陷）、docs（文档）、test（测试）、refactor（重构）、chore（构建和配置）、perf（性能）。例如 `feat(runs): 增加租约过期自动恢复`。

**ADR 模板**：

```markdown
# ADR-000X：标题

- 状态：已接受 / 提议中 / 已废弃
- 日期：YYYY-MM-DD
- 相关文档：链接

## 背景
什么约束或者问题让我们必须做这个决定？把当时的处境写清楚。

## 决策
我们决定做什么？用一两句话说明白。

## 备选方案
至少列出两个备选方案，分别写清楚优缺点，以及为什么没有选它们。

## 后果
这个决定带来什么好处？有什么代价？需要跟进哪些事情？
```

### 附录 F：时间不够时的压缩路径

压缩的原则是：**隔离、证据、版本、恢复、关键测试不能删除**，只能压缩范围。这五样东西对应 [开发方案.md](./开发方案.md) 第 11 节里的明确要求。

**八周压缩版**（适合有基础或者有人指导，每周投入三十小时以上）：

- 重点章节从五类减少到三类，例如施工方案、质量保证、安全文明施工。
- 前端只做五个页面：登录、项目列表、资料中心、章节工作台、审查与导出合并页。
- 版本比较只做并排的文本差异，不做复杂的高亮对比。
- 监控只保留指标接口和一个简单面板，不做完整的告警体系。
- 评测样本减少到两个项目，指标照常报告，但如实说明样本量小。
- 阶段一完整保留；阶段二的 B1、B2、B3 完整保留；B4 只做词项检索和模拟向量；C3 的恢复测试全部保留。

**最小可演示版**（时间再砍一半时）：

- 只实现审阅版导出，提交草稿暂时不做，界面明确写"暂不支持"。
- 只做一类重点章节，审查只做规则检查加简化语义检查。
- 用模拟模型完成全部演示，云端接入写进后续计划。
- 仍然保留：租户隔离、审计记录、版本不可变、幂等、租约恢复、跨组织负面测试。

无论怎么压缩，两条底线不能碰：**不虚构没有测量过的指标，不公开未经授权的资料。**
